# 毎月DB(Excel) ⇔ Dataverse 同期設計書

対象: ローカルPC(Windows 11)上の Excel「毎月DB」を、Microsoft 365 Business Standard with Copilot と Power Automate Premium で Dataverse と同期する。入力・同期はいずれも Power Automate で行う。

> **Dataverse for Teams の廃止決定(2027-10-30 撤去)に伴い、本格版 Dataverse を前提とする構成に改訂した。**
> この変更により **Power Automate Premium が必須**になる。詳細と根拠は 0-2 を参照。

---

## 0. 確定した前提条件

### 0-1. 業務前提(ヒアリング確定分)

| 項目 | 確定内容 | 設計への影響 |
|---|---|---|
| 行の一意キー | **受注No + 手配票No + sub_no** | 明細行番は業務システムから出力不可 → Office Script が出現順で自動採番(1-1) |
| 更新されるファイル | **最新月の1ファイルのみ**(過去分は確定・不変) | 差分スキャン対象が1ファイル=最大500行。リクエスト消費が桁違いに軽い |
| 初期ロード | **初回のみ例外**でインポート機能を使用 | 100,000行を数時間で投入。以降の入力は全てPower Automate |
| 削除の扱い | **物理削除** | Excelの誤操作が即データ消失 → サーキットブレーカーが必須 |

### 0-2. ライセンス要件【前提が変わる最重要事項】

Dataverse for Teams は**廃止が決定している**。

| 段階 | 日付 |
|---|---|
| 新規環境の作成が不可に | 2026-11-15 |
| 未移行環境の停止 | 2027-09-15 |
| 未移行環境の撤去(アプリ・フロー・データごと削除) | 2027-10-30 |

本格版 Dataverse への移行は必須。ただし**移行するとライセンス要件が根本的に変わる**。

#### Microsoft 365 Business Standard with Copilot では本格版 Dataverse は使えない

Microsoft の一次情報で確認した事実。

| 確認事項 | 公式ドキュメントの記述 |
|---|---|
| Power Platform リクエスト上限 | 「Microsoft 365 apps with Power Platform access」= **6,000/24h**。割り当て表に **Copilot の行は存在しない**ため、Copilot を追加しても増えない |
| Dataverse 利用の前提 | 「**Dataverse capacity is a prerequisite** for Power Apps and Power Automate workflows to use Dataverse」 |
| 容量の付与元 | 「Every tenant with **a Power Apps license** gets default capacity」— Microsoft 365 ライセンスではなく Power Platform ライセンスが付与元 |
| Teams 環境からの移行 | 「For any standalone Power Apps or **Power Automate usage, which also includes Dataverse API access**, the Dataverse for Teams environment **needs to upgrade to Dataverse**」 |

Dataverse コネクタは**プレミアムコネクタ**であり、Dataverse for Teams 環境内に限って付帯ライセンスで使えていた。
本格版 Dataverse に移ると、この例外から外れる。

→ **必要なのは Copilot ではなく [Power Automate Premium](https://www.microsoft.com/power-platform/products/power-automate/pricing)(約 $15/ユーザー/月)。**

これは**前提3(Microsoft 365 以外の有償サービスは採用不可)に抵触する**。
この1点の決裁がプロジェクトの可否を決める。

#### 変わらない制約

ライセンスを上げても以下は効き続ける。設計から外してはいけない。

| 制約 | 値 | 影響 |
|---|---|---|
| Dataverse サービス保護制限 | 5分あたり6,000リクエスト / 同時接続約20 | **ライセンスと無関係**。並列度の上限を決める |
| Excel Online (Business) | テーブル(ListObject)のみ読める / ファイルサイズ上限 約25MB / 「行を一覧表示」は既定256件 | Excel側の改修が必須 |

### 0-3. ローカルPC → クラウドの経路

Power Automate の**クラウドフローはローカルファイルを直接読めない**。

Power Automate Premium を取得すると**オンプレミスデータゲートウェイ + File System コネクタ**が
使えるようになり、ローカルファイルを直接読む選択肢が増える。ただし本設計では採用しない。

| 方式 | 評価 |
|---|---|
| **OneDrive 同期クライアント → SharePoint**(採用) | PCがオフラインでも、同期済みのファイルをクラウド側が常に保持している。Excel Online コネクタと Office Script がそのまま使える |
| オンプレミスデータゲートウェイ + File System | **PCが起動しゲートウェイが常駐していないと同期が止まる**。さらに File System コネクタはバイト列を返すだけで、Excel のテーブルを読むには別途処理が必要。利点が無い |

→ **OneDrive 同期クライアント経由を採用する**(Business Standard に標準で含まれる)。

```
[ローカルPC C:\...\毎月DB\]  ←→ OneDrive同期クライアント ←→ [SharePoint ドキュメントライブラリ]
```

SharePoint チームサイトのライブラリを同期する構成を推奨(個人のOneDriveではなく)。
理由: 所有者が異動しても消えない / チーム全員がアクセスできる / 権限管理が揃う。

## 1. 【最重要】Excel側に必要な改修

**ここを固めないと以降のすべてが成立しない。** 順に重要。

### 1-1. 明細行番は Office Script が出現順で自動採番する【方針確定】

現行59列に、1伝票内の明細を識別する列が無い。業務システムからの出力も不可であることが確認された。 このため **Excel には列を追加せず、Office Script が読み取り時に採番する**。

```
受注No | 手配票No | sub_no | sync_key
13524  | R08-0234 | 01     | 13524R08-023401
13524  | R08-0234 | 02     | 13524R08-023402
13524  | R08-0235 | 01     | 13524R08-023501   ← 手配票No ごとに独立採番
13600  | R08-0234 | 01     | 13600R08-023401
```

採番は「ファイルの上から出てきた順」。実装は [`sync-read-script.ts`](./sync-read-script.ts) の `main()` 内 `counter` を参照。

**この方式が成立する前提(すべて確認済み)**

| 前提 | 成立しないと何が起きるか |
|---|---|
| ファイルの行順が変わらない | 並べ替えると sub_no が入れ替わり、内容が同じでも全行が更新扱いになる(最大500更新=514リクエスト) |
| 同一の受注No が複数の月ファイルに出現しない | 同期キーが月をまたいで衝突する。ただし代替キーの一意制約で「新しい行の追加」が失敗するため、無言のデータ破壊にはならず検知できる |
| 明細数が99以下 | 桁あふれ。スクリプトが例外で停止する(`MAX_LINES_PER_GROUP`) |

**残る注意点**: 行がグループの途中に挿入されると、それ以降の sub_no がズレる (末尾への追加なら影響なし)。前提上は発生しないが、万一発生した場合は 最終状態は正しくなるものの delete + create が走り、Dataverse 行の `createdon` が失われる。 週次の整合性検証フロー(5-4)で削除件数を監視すること。

**将来この前提が崩れた場合の対処**: Office Script は書き込みも可能なため、 採番結果を Excel の列に書き戻して永続化すれば、行順・挿入の双方から独立した 真に安定したキーになる。10行程度の追加で実装できる。

### 1-2. テーブル(ListObject)化

Excel Online (Business) コネクタは**セル範囲を読めない。テーブルだけ**を読む。

- 全ファイルで**同じテーブル名**にする(例: `T_DB`)。ファイルごとに名前が違うとフローが分岐地獄になる
- テーブル名を後から変えると全フローが即死する。命名は最初に固定する
- ヘッダー行は1行のみ。結合セル・空列・重複列名は不可

### 1-3. コード系列の書式を「文字列」にする

`受注No` **`手配票No`** `商品コード` `得意先コード` `担当者コード` `部門コード` `直送先コード` `見積No` `番船`

数値書式のままだと `0001` → `1` になり、Dataverse側のキーが壊れる。 **`受注No` と `手配票No` は同期キーの構成要素**なので、ここが崩れると同期そのものが破綻する。 既に壊れている過去データがあるなら、初期ロード前に一括修正する。

### 1-4. ファイル配置とファイル名規約

```
SharePoint: /毎月DB/
    current/  毎月DB_2026-08.xlsx     ← 最新月(同期対象)
    archive/  毎月DB_2026-07.xlsx     ← 確定済み(同期対象外)
              毎月DB_2026-06.xlsx
              ... (200ファイル)
    master/   区分表.xlsx
```

- `current/` に置かれた1ファイルだけを差分同期する。これで**スキャン対象が常に最大500行**に固定される
- 月次締めフローが `current/` → `archive/` へ移動する
- OneDriveの一時ファイル `~$*.xlsx` と競合コピー `*-.xlsx` はトリガー条件で除外する

### 1-5. 半角カナ・日本語列名の扱い

`ｻｲｽﾞ` `ﾌﾟﾛｼﾞｪｸﾄ名コード` `ﾌﾟﾛｼﾞｪｸﾄ名名` は半角カナ。JSONのキーとしてそのまま流れる。 Power Automate の式で `item()?['ｻｲｽﾞ']` と書けば動作はするが、

- 全角/半角のゆらぎ(`ｻｲｽﾞ` vs `サイズ`)で無言で null になる
- 式のコピペ時に文字化けする
- 60個の式を目視でレビューできない

→ **Office Script の読み取り時点で ASCII 論理名へ正規化する**(後述)。 Excel側の列名は現状のまま変えなくてよい。

## 2. 【最重要】リクエスト予算の設計

### 2-1. 予算

| 項目 | 件数/日 |
|---|---|
| 割り当て(Power Automate Premium) | 40,000 |
| トリガーポーリング(15分間隔 × 1フロー) | 96 |
| トリガーポーリング(月次締め・区分表・検証フロー) | 約 30 |
| **同期処理に使える実質予算** | **約 39,800** |

Dataverse for Teams 時代の 6,000 件から 6.6 倍になった。ただし**以降の節で述べる技法1〜4はそのまま残す**。
余裕ができたから雑に作ってよい、という話にはならない。理由は3つ。

1. **Dataverse のサービス保護制限(5分あたり6,000)はライセンスと無関係に効く。**
   結局ループは絞る必要がある
2. **実変更量に比例する設計のほうが、障害時の復旧と原因特定が速い。**
   500行保存して3行しか書かない設計なら、ログに出る書き込みが常に「実際に起きた変更」と一致する
3. **Premium を手放す判断が将来あっても、設計を作り直さずに済む**

### 2-2. 素直に作ると破綻する

500行を `Apply to each` で回し、中で「Dataverseから行を検索」→「条件分岐」→「作成 or 更新」とすると、 1行あたり3〜5リクエスト → **500行で1,500〜2,500件**。さらに区分列7本をルックアップで解決すると **+3,500件/500行**。
40,000 の予算なら一見収まるが、**Dataverse のサービス保護制限(5分あたり6,000)に先にぶつかって 429 が多発する**。
リクエスト予算ではなくスループットの問題として、ループは絞る必要がある。

### 2-3. リクエストを最小化する技法

これが本設計の核心。**「ループの中に置くDataverseアクションを1個だけにする」**ことが目標。
技法1〜4は Premium の有無にかかわらず有効で、代替案A(SharePoint リスト)にもそのまま流用できる。

#### 技法1: 配列操作アクションは件数に関係なく1リクエスト

`アイテムの選択(Select)` `配列のフィルター処理(Filter array)` `作成(Compose)` `結合(Join)` は、 配列が500件でも**1回の実行で1リクエスト**。差分計算をすべてこれで行う。

#### 技法2: JSONオブジェクトを辞書として使い、O(1)ルックアップを実現

Power Automate の式には `filter()` が無い。そのため「このキーに対応するDataverseのGUIDは?」を ループ内で引こうとすると `Filter array` を回すことになり **+1リクエスト/行**。

これを回避する。Dataverseから取得した配列を、キー→値の**JSONオブジェクト(辞書)**に変換する。

```
[1] アイテムの選択 「Select_GUID」
    差し込み元: outputs('Dataverse行の一覧')?['body/value']
    マップ(テキストモード):
      concat('"', item()?['crfff_sync_key'], '":"', item()?['crfff_meisaiid'], '"')

[2] 作成 「GUID辞書」
    json(concat('{', join(body('Select_GUID'), ','), '}'))

[3] 参照(ループ内、追加リクエストゼロ)
    outputs('GUID辞書')?[items('更新ループ')?['sync_key']]
```

3アクション(=3リクエスト)で500件分の辞書ができる。同じ要領で `HASH辞書` `EXCELキー辞書` を作る。

> キーに `"` や `\` が含まれると JSON が壊れる。`sync_key` は Office Script 側で `[^0-9A-Za-z\-_]` を除去してサニタイズしておく。

#### 技法3: 差分を「新規/更新/削除」の3配列に事前分割する

ループ内に条件分岐を置くと、分岐アクション自体が1リクエスト/行。 分割を `Filter array` 3個(=3リクエスト)で済ませ、ループ内はDataverseアクション1個だけにする。

```
新規 = Filter(Excel行, @equals(outputs('GUID辞書')?[item()?['sync_key']], null))

更新 = Filter(Excel行, @and(
          not(equals(outputs('GUID辞書')?[item()?['sync_key']], null)),
          not(equals(outputs('HASH辞書')?[item()?['sync_key']], item()?['row_hash']))))

削除 = Filter(Dataverse行, @equals(outputs('EXCELキー辞書')?[item()?['crfff_sync_key']], null))
```

#### 技法4: 行ハッシュで「実際に変わった行」だけ書く

Excelの保存操作は全行を等しく「更新されたかもしれない行」にしてしまう。 59列を連結したハッシュを行ごとに持ち、Dataverse側の値と一致する行は**一切書かない**。

Power Automate の式には `sha256()` などのハッシュ関数が無い。 連結文字列をそのまま保存する手もあるが、`備考` が長いと数千文字になり容量を食う。

→ **Office Script 内で FNV-1a を計算し、16桁の16進文字列にする**(後述)。

#### 技法5: OData `$batch` で書き込みを一括化する【Premium で新たに可能】

Power Automate Premium では **HTTP with Microsoft Entra ID** コネクタが使える。
Dataverse Web API の `$batch` エンドポイントに複数の操作をまとめて送れる。

```
POST https://<org>.crm7.dynamics.com/api/data/v9.2/$batch
Content-Type: multipart/mixed; boundary=batch_sync

--batch_sync
Content-Type: multipart/mixed; boundary=changeset_1

--changeset_1
Content-Type: application/http
Content-Transfer-Encoding: binary

POST /api/data/v9.2/crfff_meisais HTTP/1.1
Content-Type: application/json

{"crfff_sync_key":"13524R08-023401", "crfff_order_no":"13524", ...}
--changeset_1
  (以下、操作を繰り返す)
--changeset_1--
--batch_sync--
```

Power Platform リクエストとしては **HTTP アクション1回 = 1件**。
500行の書き込みが **500リクエスト → 数リクエスト**になる。

**ただし、最初からこれを使うことは推奨しない。** 理由は3つ。

1. **サービス保護制限はバッチの中の操作数で評価される。** 1バッチあたり100〜200操作に抑える必要があり、
   「1リクエストで何でも入る」わけではない
2. **changeset 内はトランザクション。** 1件失敗すると全体がロールバックするため、
   どの行が原因かの特定が難しくなる。500行のうち1行だけ日付が壊れていた、という状況で切り分けできない
3. **JSON と multipart の組み立てが複雑**で、フローの可読性が大きく落ちる

→ **初期ロードや月次の全入替のような大量書き込み専用の手段として持っておく。**
日常の数件〜数十件の更新は、素直な Dataverse コネクタのほうが運用しやすい。
まず技法1〜4だけで運用を開始し、実測して必要になってから導入すること。

### 2-4. 結果として得られるリクエスト消費

固定オーバーヘッドは **1同期あたり14リクエスト**。

| ステップ | リクエスト |
|---|---|
| 同期制御テーブルの取得 | 1 |
| Excel スクリプトの実行 | 1 |
| Dataverse 行の一覧(500行、select指定) | 1 |
| アイテムの選択 × 3 | 3 |
| 作成(辞書) × 3 | 3 |
| 配列のフィルター処理 × 3 | 3 |
| 削除件数チェック(条件) | 1 |
| 同期制御の更新 | 1 |
| **小計** | **14** |
| 新規N件 + 更新M件 + 削除K件 | N + M + K |

**合計 = 14 + (実際に変わった行数)** — これが理論最小値。

## 3. Dataverse テーブル設計

### 3-1. テーブル一覧

| テーブル | 論理名 | 用途 | 想定行数 |
|---|---|---|---|
| 毎月DB明細 | `crfff_meisai` | 本体 | 100,000 → +6,000/年 |
| 区分マスタ | `crfff_kubun` | 区分表(5行2列) | 5 |
| 同期制御 | `crfff_synccontrol` | ファイル単位の同期状態 | 201 |
| 同期エラー | `crfff_syncerror` | 失敗行の記録 | 変動 |

> `crfff_` は発行者プレフィックスの仮置き。本格版 Dataverse では**ソリューションの発行者を自分で定義できる**ため、
> `nlm_` のような意味のある接頭辞を最初に決めること。後から変更すると全列の再作成になる。

### 3-2. 毎月DB明細 — 管理列

| 表示名 | 論理名 | 型 | 備考 |
|---|---|---|---|
| 同期キー | `crfff_sync_key` | テキスト(100) | **主名前列 かつ 代替キー**。`受注No + 手配票No + sub_no(2桁ゼロ埋め)` を区切り無しで連結 |
| 受注No | `crfff_order_no` | テキスト(30) | キー構成要素 |

### 3-4. 型選択の根拠(ここを間違えると後戻りできない)

#### 通貨型を使わない

金額列(原価/受注金額/粗利益/売価金額/標準価格/内税額/外税額/受注残高)は **10進数** にする。 Dataverse の**通貨型**を選ぶと、

- `transactioncurrencyid`(通貨へのルックアップ)と `exchangerate` が暗黙に必要になる
- 列ごとに `_base` 列(基準通貨換算値)が自動生成され、**列数と容量が実質2倍**になる
- 書き込みのたびに通貨解決が走り、フローが複雑化する

単一通貨(円)しか扱わないなら通貨型は害しかない。

#### 日付は「日付のみ / タイムゾーン非依存」

`受注日` `納期` を「日付と時刻」型にすると、Dataverse は UTC で保存しユーザーのタイムゾーンで表示する。 JST(+9)環境では **2026-08-04 が 2026-08-03 と表示される事故**が起きる。 「日付のみ」+ 動作「タイムゾーンに依存しない」を必ず選ぶ。**この設定は後から変更できない。**

#### テキスト長を既定の100/4000のままにしない

Dataverse は実データ長で消費するが、長すぎる定義はインデックス・検索列の効率を落とす。 逆に短すぎると同期が失敗する。実データの最大長を調べて +50% 程度で設定する。

#### 論理名は必ず小文字になる — `crfff_RNo` の落とし穴

Dataverse の**論理名(logical name)は常に小文字**に正規化される。 列作成時に表示名「手配票No」、スキーマ名 `crfff_RNo` と入力しても、 Web API と Power Automate の Dataverse コネクタが使う論理名は **`crfff_rno`** になる。

- Office Script が返す JSON キーは `RNo`(本書の表記どおり)
- フローで Dataverse 列に書き込む際の参照名は **`crfff_rno`**(小文字)

他の58列は元から小文字なのでこの問題は起きない。**大文字を含むのは `RNo` だけ**なので、 ここだけ取り違えると「その列だけ無言で値が入らない」という切り分けの難しい障害になる。

#### 監査(Auditing)をOFFにする

テーブルの監査をONにすると、更新のたびに監査ログ行が生成される。 毎日500行更新する運用では**本体データより監査ログのほうが大きくなる**。
本格版 Dataverse では 2 GB のハード上限は無いが、テナント共有の容量プールを圧迫する(3-7)。
必要なら Dataverse ではなく SharePoint リストに変更履歴を出す。

### 3-5. 区分マスタと、追加リクエストゼロのルックアップ解決

**マスタ1本で7列すべてを賄えることが確認済み**のため、区分種別は不要。代替キーは単一列になる。

```
区分マスタ (crfff_kubun)
  crfff_kubun_code   テキスト(10)   区分コード   ← 代替キー(単一列)
  crfff_kubun_name   テキスト(50)   区分名       ← 主名前列
```

参照する列は7本。すべて同じ区分マスタへのルックアップになる。

| 参照元の列 | ルックアップ列の論理名 |
|---|---|
| データ区分 | `crfff_data_kubun` |
| 原価税込区分 | `crfff_cost_taxincl_kubun` |
| 税込区分 | `crfff_taxincl_kubun` |
| 単位区分 | `crfff_unit_kubun` |
| 軽減税率マーク | `crfff_reduced_tax_mark` |
| 原価軽減税率マーク | `crfff_cost_reduced_tax_mark` |
| 出荷マーク | `crfff_ship_mark` |

> 同一テーブルへのルックアップを7本作るため、**リレーションシップのスキーマ名が7つとも 重複しない**ように命名する必要がある(既定名は衝突する)。列作成時に個別に指定すること。

> **注意**: マスタを共有するため、列ごとに値域を絞ることはできない。 例えば `出荷マーク` に `単位区分` 用のコードを入れても Dataverse は受け付ける。 値の妥当性は Excel 側の入力規則か、週次の整合性検証フロー(5-4)で担保する。

**素直にやると破綻する**: ルックアップ列に値を入れるには通常、対象行のGUIDが要る。 ループ内で「区分マスタから行を取得」を7回やると **+3,500リクエスト/500行**。

**解決策 — 代替キーによる `@odata.bind`**: Dataverse コネクタの「新しい行の追加」のルックアップ欄に、GUIDではなく **代替キー参照の文字列**を直接入れる。Dataverse サーバー側で解決されるため **追加リクエストは発生しない**。

```
/crfff_kubuns(crfff_kubun_code='01')
```

式にすると(Power Automate ではシングルクォートを2つ重ねてエスケープする):

```
concat('/crfff_kubuns(crfff_kubun_code=''', items('新規ループ')?['data_kubun'], ''')')
```

> 本格版 Dataverse では代替キーの作成に制約が無い(Teams 環境では作成可否がテナント設定に左右されていた)。
> なお、フロー冒頭で区分マスタ5行を1回だけ取得し(=1リクエスト)、技法2の辞書に載せて GUID を引く方法も同じコストで済む。
> **代替案A(SharePoint リスト)に切り替える可能性があるなら、辞書方式のほうが移植しやすい。**

**区分列に空欄がある場合の扱い**

区分コードが空だと `/crfff_kubuns(crfff_kubun_code='')` になり、該当行が無いため **Dataverse が 404 を返してその行の作成が失敗する**。区分列は7本あるので、 7倍の確率でこれを踏む。

対処は2つ。**推奨は前者**。

1. **区分マスタに「未設定」行を1本追加する**(`__NONE__` / 未設定)。 Office Script 側で空を `__NONE__` に寄せる。フローに分岐が不要で、 集計時に「未設定が何件あるか」が見えるという利点もある
2. フロー側で `if(empty(...), null, concat(...))` と分岐する。 7列すべてに書く必要があり、式が読みにくくなる

現時点で区分列に空欄が入るかは未確認(0-5)。**入らないなら何もしなくてよい。**

### 3-7. 容量見積り

| 内訳 | 1行あたり |
|---|---|
| テキスト列 35本 × 平均12文字 × 2byte | 約 840 B |
| 数値・日付列 17本 × 8byte | 約 136 B |
| ルックアップ 7本 × 16byte | 約 112 B |
| Dataverse システム列オーバーヘッド | 約 800〜1,000 B |
| **計** | **約 2.0〜2.5 KB** |

- 100,000行 → **200〜250 MB**
- 年間増加 12ファイル × 500行 = 6,000行 → **約 15 MB/年**

本格版 Dataverse では容量が**テナント単位のプール**になり、Dataverse for Teams の 2 GB/環境という
ハードな上限は無くなる。付与元は以下。

| 付与元 | Dataverse Database 容量 |
|---|---|
| テナント既定容量(最初の Power Apps / Power Automate ライセンス購入時) | 一般に 10 GB |
| Power Automate Premium 1ライセンスあたり | + 250 MB |
| Power Apps Premium(per user) 1ライセンスあたり | + 250 MB |

**2 GB の壁は消えたが、代わりに注意点が2つ増えた。**

1. **容量はテナント共有のプール。** 他部署が Dataverse を使い始めると食い合う。
   本設計だけを見て「10 GB あるから余裕」と判断してはいけない
2. **実際の空き容量は Power Platform 管理センター → リソース → 容量 で必ず確認する。**
   テナントごとに購入履歴が違うため、上表は目安でしかない。**着手前に実測すること**

**監査(Auditing)は引き続き OFF を推奨。** 2 GB の壁は無くなったが、毎日500行更新する運用では
監査ログが本体データを上回り、テナント全体の容量を圧迫する。
変更履歴が必要なら SharePoint リストへ出す。

## 4. Office Script(読み取り・正規化・ハッシュ生成)

Excel Online (Business) の「スクリプトの実行」は**標準コネクタのアクション**。 1リクエストで以下をすべて処理でき、フロー側のアクション数を劇的に減らせる。

- テーブル `T_DB` が無ければ作成する(冪等。毎月の手作業が不要になる)
- テーブル全体を読む(「行を一覧表示」の256件ページングが不要)
- 半角カナ・日本語の列名 → ASCII論理名に正規化
- 日付シリアル値 → ISO文字列に変換
- 空白セル・不可視文字(ZWSP等) → null に正規化
- 受注No + 手配票No ごとに出現順で `sub_no` を採番し、同期キーを生成
- 行ハッシュ(FNV-1a 16桁hex)の生成

### 実装

**完全なコードは [`sync-read-script.ts`](./sync-read-script.ts) を参照。** 本書には転記しない(二重管理になり、必ず片方が古くなるため)。

同ファイルは `tsc` による型チェックと、採番・ハッシュ・正規化・異常系を含む 動作テストを通している。Office Scripts エディタへはそのまま貼り付けられる。

### 設計上の要点

| 要点 | 内容 |
|---|---|
| 同期キー | `受注No + 手配票No + sub_no(2桁)` を**区切り無しで連結**。例: `13524` + `R08-0234` + `01` → `13524R08-023401` |
| 採番の単位 | 受注No + 手配票No。片方の手配票No に行を足しても、他方の番号は動かない |
| 行ハッシュ | 業務列59本のみ。`sub_no` は含めない(採番はキー側の責務) |
| 列の並び順 | `COL_MAP` のキー順がハッシュの計算順を決める。**並び替えると全行のハッシュが変わり、現在月の全行が更新対象になる** |
| 解釈できない値 | null に丸めず**例外で同期全体を止める**。`納期` に `未定` が入っていた行だけが静かに欠落する事故を防ぐ |
| エラーメッセージ | 必ず Excel の行番号を含める。500行のどこが原因かを即座に特定できる |

### 異常系で停止する条件

いずれも Excel の行番号付きで例外を投げ、同期を中断する。

- 列が見つからない(`COL_MAP` と Excel ヘッダーの不一致)
- `受注No` または `手配票No` が空 — 同期キーの構成要素は空にできない
- `受注No` または `手配票No` に英数字・ハイフン・アンダースコア以外の文字
- `受注日` / `納期` が日付として解釈できない(`未定` `-` `※` など)
- 数値列が数値として解釈できない
- 同一グループの明細が99行を超えた
- 同期キーが重複した(区切り無し連結による桁の食い違い。Dataverse の代替キー制約でも検知されるが、こちらのほうが原因が分かりやすい)

### 4-1. Office Script の制約と対策

| 制約 | 影響 | 対策 |
|---|---|---|
| ファイルが OneDrive/SharePoint 上にある必要がある | — | 本設計は元々SharePoint配置 |
| テナントで Office Scripts が無効化されている場合がある | 使えない | Microsoft 365 管理センターで有効化。不可なら「テーブルに存在する行を一覧表示」+ Select にフォールバック(リクエスト +5〜10) |
| 戻り値のペイロードに上限がある | 500行×59列は約1MB前後で収まる見込みだが、`備考` が長いと超える可能性 | 250行ずつ2回に分割、または `備考` を別スクリプトで取得 |
| スクリプト実行時間の上限 | 500行なら問題なし | — |
| ファイルがユーザーに開かれてロック中 | 読み取り自体は可能だが「編集途中」を同期しうる | 後述のデバウンス |

### 4-2. Office Scripts が使えない場合のフォールバック

Excel側の各ファイルに補助列を2本追加する。

```
_sub_no    = COUNTIFS($受注No$2:受注No2, 受注No2, $手配票No$2:手配票No2, 手配票No2)
_同期キー   = 受注No2 & 手配票No2 & TEXT(_sub_no,"00")
_行ハッシュ = TEXTJOIN("|",FALSE, TEXT(受注日,"yyyy-mm-dd"), TEXT(納期,"yyyy-mm-dd"), A2, B2, ...)
```

`_sub_no` は先頭行からの累積 COUNTIFS で「受注No + 手配票No 単位の出現順」を再現する。

デメリット: 500行×数式3本がファイルを重くする(COUNTIFS の累積参照は特に重い) / 日付の書式指定漏れでハッシュが毎回変わる / テーブル作成の自動化ができない / 値の正規化(先行ゼロ・不可視文字・日付の文字列混入)を数式で再現しきれない。 **Office Script が使えるならそちらを強く推奨。**

## 5. フロー設計

### 5-1. フロー① 最新月ファイル差分同期(メイン)

**トリガー**: SharePoint「ファイルが作成または変更されたとき(プロパティのみ)」

- ライブラリ: `毎月DB`、フォルダー: `/current`
- ポーリング間隔: **15分**(5分にするとポーリングだけで288リクエスト/日)
- 同時実行制御: **ON / 並列度1**(直列化。二重実行による競合を防ぐ)

**ステップ**

| # | アクション | 内容 |
|---|---|---|
| 1 | トリガー | ファイル変更検知 |
| 2 | 条件 | ファイル名が `~$` で始まる → 終了 |
| 3 | Dataverse 行を一覧表示 | 同期制御(`file_name eq ''`) |
| 4 | 条件(デバウンス) | `最終同期日時` から3分以内 → 終了。編集中の連続保存で無駄打ちしない |
| 5 | Excel スクリプトの実行 | 上記 Office Script → `excelRows[]` |
| 6 | Dataverse 行を一覧表示 | `crfff_meisais`、filter `crfff_source_file eq ''`、**select `crfff_sync_key,crfff_row_hash,crfff_meisaiid`** |
| 7 | Dataverse 行を一覧表示 | 区分マスタ(5行) |
| 8-10 | アイテムの選択 × 3 | GUID / HASH / EXCELキー の辞書材料 |
| 11-13 | 作成 × 3 | `json(concat('{', join(...), '}'))` |
| 14-16 | 配列のフィルター処理 × 3 | 新規 / 更新 / 削除 |
| 17 | 条件(サーキットブレーカー) | 削除件数 > max(20, 既存件数 × 0.2) → 中断してTeamsに通知 |
| 18 | Apply to each(新規) | 新しい行の追加。**並列度 20** |
| 19 | Apply to each(更新) | 行の更新。行ID = `outputs('GUID辞書')?[items(...)?['sync_key']]`。**並列度 20** |
| 20 | Apply to each(削除) | 行の削除。**並列度 20** |
| 21 | Dataverse 行の更新 | 同期制御を更新 |
| 22 | スコープ(実行後: 失敗時) | 同期エラーに記録 + Teamsに通知 |

**主要な式**

```
■ Select_GUID (差し込み元: outputs('Dataverse行の一覧')?['body/value'])
  concat('"', item()?['crfff_sync_key'], '":"', item()?['crfff_meisaiid'], '"')

■ Select_HASH
  concat('"', item()?['crfff_sync_key'], '":"', coalesce(item()?['crfff_row_hash'],''), '"')

■ Select_EXCELKEY (差し込み元: body('スクリプトの実行')?['result'])
  concat('"', item()?['sync_key'], '":1')

■ 作成「GUID辞書」
  json(concat('{', join(body('Select_GUID'), ','), '}'))

■ フィルター「新規」   差し込み元: body('スクリプトの実行')?['result']
  @equals(outputs('GUID辞書')?[item()?['sync_key']], null)

■ フィルター「更新」   差し込み元: body('スクリプトの実行')?['result']
  @and(
    not(equals(outputs('GUID辞書')?[item()?['sync_key']], null)),
    not(equals(outputs('HASH辞書')?[item()?['sync_key']], item()?['row_hash']))
  )

■ フィルター「削除」   差し込み元: outputs('Dataverse行の一覧')?['body/value']
  @equals(outputs('EXCELキー辞書')?[item()?['crfff_sync_key']], null)

■ 更新ループ内の行ID
  outputs('GUID辞書')?[items('更新ループ')?['sync_key']]

■ 区分ルックアップ(代替キー方式)
  concat('/crfff_kubuns(crfff_kubun_code=''',
         coalesce(items('新規ループ')?['data_kubun'], ''), ''')')
  ※ 区分が空の行があるなら、空のときはルックアップ欄を null にする分岐が要る
```

**Dataverse 行の一覧表示で `select` を必ず指定する理由** 指定しないと59列すべてが返り、500行で数MBのペイロードになる。 辞書化に必要なのは `sync_key` `row_hash` `GUID` の3つだけ。転送量とタイムアウトの両方に効く。

### 5-2. フロー② 月次締め

- トリガー: 繰り返し(毎月1日 02:00 / または手動)
- フロー①を最後に1回実行 → `current/` のファイルを `archive/` へ移動 → 同期制御の状態を「確定」
- 新しい月のファイルを `current/` に配置 → 同期制御に新規行を作成
- **削除サーキットブレーカーをこのフローでは一時的に緩和する**(全行入替が正常な操作になるため)

### 5-3. フロー③ 区分マスタ同期

- トリガー: `master/区分表.xlsx` の変更
- 5行なので技法を使わず素直に回してよい(10リクエスト程度)

### 5-4. フロー④ 整合性検証(週次)

- トリガー: 繰り返し(毎週月曜 07:00)
- Excel件数 vs Dataverse件数、ハッシュ不一致件数を比較 → Teamsチャネルに投稿
- **物理削除を採用しているため、これが実質的な唯一の安全網になる**

### 5-5. エラー処理

| 事象 | 挙動 | 対策 |
|---|---|---|
| Dataverse 429(サービス保護制限) | Power Automate が自動リトライ(既定4回・指数バックオフ) | リトライもリクエストを消費する。並列度を20以下に抑えて発生自体を減らす |
| 一部の行だけ失敗 | 既定では以降のループも継続 | スコープ+「実行後の構成: 失敗時」で同期エラーテーブルに記録 |
| フロー全体の失敗 | ハッシュが更新されないので次回再試行される | **冪等性が保証されているため、そのまま再実行して安全** |
| Excelがロック中 | 読めるが編集途中の可能性 | デバウンス(3分)+ 同時実行制御 |

## 6. 初期ロード(初回のみ例外を使う)

### 6-1. 手順

**Step 1 — ローカルPCで200ファイルを統合CSVにする(Power Query)**

Excel を新規作成 → データ → データの取得 → ファイルから → フォルダーから → `archive` フォルダーを指定 → 「データの変換」

```
1. Content 列以外を削除
2. カスタム列: Excel.Workbook([Content])
3. 展開 → Kind = "Table" かつ Name = "T_DB" の行だけ残す
4. Data 列を展開(59列 + _明細行番)
5. Source.Name から source_file 列を作る
6. カスタム列 sync_key = [受注No] & "-" & Text.PadStart(Text.From([_明細行番]), 4, "0")
7. 受注日 / 納期 を「日付」型に、コード系を「テキスト」型に明示変換
8. 閉じて読み込む → CSV(UTF-8 BOM付き)としてエクスポート
```

**Step 2 — 行ハッシュは空のままにする**

初期ロードのハッシュ計算(Power Query)と定常同期のハッシュ計算(Office Script)を 完全に一致させるのは事実上不可能。**わずかな差でも初回同期で全10万行が更新対象になり、 リクエスト上限を確実に突破する。**

回避策:

- `archive/` の行は**同期対象外**なのでハッシュは不要 → 空(null)のまま
- `current/` の当月分だけは、初期ロード後に**フロー①を1回流してハッシュを埋める**(500行=約514リクエスト)
- 空ハッシュの行は `not(equals(null, row_hash))` が真になるため、自動的に更新対象になる。想定通りの挙動

**Step 3 — make.powerapps.com からインポート**

1. `make.powerapps.com` → 環境セレクタで Day 0 で作成した運用環境を選択
2. テーブル → 毎月DB明細 → データのインポート → テキスト/CSV から
3. 列マッピングを設定。区分列は代替キー(`区分コード`)で解決
4. 10万行なら 1万行 × 10ファイルに分割すると失敗時の切り分けが楽

> 本格版 Dataverse では、1回のインポートの上限に達した場合でも `$batch`(技法5)による投入が選べる。
> 40,000/日の予算があるため、素直なコネクタでも 100,000行 を約3日で投入できる。

**Step 4 — 検証**

フロー④を手動実行し、Excel件数とDataverse件数、サンプル100行の値一致を確認。

### 6-2. 前提4(入力はPower Automateのみ)を厳守する場合(参考)

| 方式 | 所要 | 備考 |
|---|---|---|
| 単一アカウント日次分割 | **約3日** | Premium の 40,000/日 により、6,000/日 時代の20日から大幅短縮 |
| 5ユーザーに分散 | 1日未満 | リクエストは**ユーザー単位**。Premium 環境では分散する必要がまず生じない |
| 直近24ヶ月のみ投入 | 約2日 | 12,000行。古いデータは SharePoint 上の Excel を Power Query で参照 |

## 7. 具体例(リクエスト消費のトレース)

### 例1 — 最新月ファイルに新規10行を追加して保存

| 内訳 | リクエスト |
|---|---|
| トリガーポーリング(この回) | 1 |
| 固定オーバーヘッド | 14 |
| 新規作成 10行 | 10 |
| **合計** | **25** |

日次予算 5,800 に対して 0.4%。1日230回やっても収まる。

### 例2 — 既存500行のうち3行の単価を修正して保存

| 内訳 | リクエスト |
|---|---|
| 固定オーバーヘッド | 14 |
| 更新 3行 | 3 |
| **合計** | **17** |

**残り497行はハッシュが一致するため一切書き込まれない。** これが技法4の価値で、ハッシュ無しなら500リクエスト消費していた。

### 例3 — 500行を全入れ替え(前月分を削除して当月分を貼り付け)

| 内訳 | リクエスト |
|---|---|
| 固定オーバーヘッド | 14 |
| 削除 500行 | 500 |
| 新規 500行 | 500 |
| **合計** | **1,014** |

日次予算の 17%。1日5回までなら安全、6回目でリスク域。

ただし**削除500件は全体の100%**なのでサーキットブレーカーが作動して中断する。 これは意図通りの動作で、「全入替」は月次締めフロー②で明示的に許可された操作としてのみ実行する。 通常運用中にこれが起きたら、それは高確率で事故(フィルター状態で保存した、別月ファイルを上書きした等)。

## 8. メリット / デメリット

### メリット

1. **リレーショナルな型・一意制約・参照整合性**が効く。素のExcelでは不可能な整合性担保
2. **リクエスト消費が実変更量に比例**。500行保存しても変更0なら書き込み0
3. **完全な冪等性**。代替キー+ハッシュ設計により、何度流しても結果が同じ。失敗しても再実行するだけ
4. **容量のハード上限が無くなった**(2 GB/環境 → テナントプール)。履歴・ログの選択肢が戻る
5. **列レベルセキュリティが使える。** `原価` `粗利益` `利益率` を特定メンバーにだけ見せる運用が可能
6. **バックアップ / 復元 / 環境のコピーが使える。** 本番を複製した検証環境を作れる
7. **環境が Teams のチームから独立する。** チームを削除してもデータは消えない
8. **プラグイン / カスタム API** でサーバー側のバリデーションと一括処理ができる
9. **プレミアムコネクタとオンプレミスデータゲートウェイ**が使え、将来の拡張余地が大きい
10. **リクエスト上限が 6,000 → 40,000**。大量更新や初期ロードの現実性が上がる
11. **最新月1ファイルのみ更新という業務特性が、この構成に理想的に噛み合う**

### デメリット

1. **Power Automate Premium のライセンス費用が発生する**(約 $15/ユーザー/月)。**前提3に抵触する**
2. **容量がテナント共有プールになり、他部署と食い合う。** 2 GB の上限と引き換えに、
   自分だけでは制御できない変数が増えた
3. **運用負荷が上がる。** Power Platform 管理センター、ソリューション、DLP ポリシー、
   環境のライフサイクル管理の知識が必要になる。Teams 環境は「作れば動く」だったがそうではなくなる
4. **接続の所有者が単一障害点。** 所有者の退職・パスワード変更・MFA再認証で全フローが停止する
5. **Excel Online コネクタが脆い。** テーブル名変更・ファイル移動・ファイルサイズ超過で即死
6. **OneDrive同期の遅延と競合。** PCがスリープ/オフラインだと同期されず、競合コピーが発生しうる
7. **Excel側の改修が必須**(コード列の文字列書式化)。既存業務手順に影響する
8. **障害の切り分けが5層にまたがる**(Excel / OneDrive / SharePoint / Power Automate / Dataverse)

## 9. 見落としやすい弱点(率直な指摘)

重要度順。

### 1. ライセンス未決裁のまま設計を進めるリスク — 最大の落とし穴

本格版 Dataverse は **Power Automate Premium 無しでは動かない**(0-2)。
Copilot を足しても解決しない。

この決裁が取れないまま Excel 側の改修や Office Script の実装を進めると、
**作ったものが丸ごと使えなくなる**。先に決裁を取るか、少なくとも
「取れなかった場合は代替案A(SharePoint リスト)へ切り替える」と決めてから着手すること。

代替案Aへの切り替えはフロー構造(技法1〜4)をほぼ流用できるため、
**Excel 側の改修と Office Script は無駄にならない**。切り替え点はDataverseコネクタの
部分だけ。この事実が分かっていれば並行して進めてよい。

### 2. 物理削除 + Excelの誤操作 = 復旧不能

以下はすべて「Excel上で行が消えたように見える」操作で、そのままDataverseの物理削除につながる。

- オートフィルターで絞り込んだ状態のまま別ファイルとして保存した
- 誤って行を削除して気づかず保存した
- 前月のファイルを `current/` に置いてしまった

**サーキットブレーカーは必須**: 1回の同期で削除対象が `max(20件, 既存件数の20%)` を超えたら
中断してTeamsに通知し、人間が承認するまで実行しない。実装コストは条件アクション1個(1リクエスト)。

さらに、**論理削除への変更を再検討する価値が上がった**。
本格版 Dataverse では容量のハード上限が無くなったため、削除フラグ列を持つコストが
実質ゼロになっている。物理削除を選ぶ積極的な理由が「Excelと完全一致させたい」だけなら、
フロー④の整合性検証で同じ目的が達成できる。

### 3. サービスアカウントに Premium ライセンスが要る

個人アカウントでフローを作ると、その人の異動・退職・パスワード変更・MFA再認証で
**全フローの接続が無効化され、同期が無言で止まる**。
同期専用アカウント(例: `svc-dbsync@...`)を用意するのが正しい。

**本格版 Dataverse では、このアカウントにも Power Automate Premium が必要**になる。
Business Standard 1本では足りない。ライセンス費用を見積もる際はここを忘れないこと。

### 4. Dataverse サービス保護制限と並列度 — 重要度が上がった

「ライセンスが 40,000 になったから並列度を上げれば速い」は**誤り**。

Dataverse のサービス保護制限(5分あたり6,000リクエスト / 同時接続約20)は
**ライセンスと無関係に効く**。上げすぎると 429 が返り、リトライが発生し、
リトライもリクエストを消費するため予算が悪化する。
`Apply to each` の並列度は 20 前後を上限とする。

リクエスト予算が緩んだぶん、**律速はライセンスではなくサービス保護制限側に移った**。

### 5. 容量がテナント共有プールになった

2 GB/環境 のハード上限は消えたが、代わりに**自分で制御できない変数が増えた**。
他部署が Dataverse を使い始めると容量を食い合う。
着手前に Power Platform 管理センター → リソース → 容量 で実際の空きを確認し、
定期的に監視すること。

### 6. 区分マスタを7列で共有することの副作用【確認済み・要注意】

区分表1本(5行)で7列すべてを賄えることは確認済み。ただしマスタを共有する以上、
**列ごとに値域を絞ることができない**。

例えば `出荷マーク` に `単位区分` 用のコードを入れても、Dataverse はルックアップとして
正当なので受け付ける。「その列に入ってよい値か」の検証はどこにも存在しない。

対処:
- Excel 側の入力規則(データの入力規則 → リスト)で列ごとに候補を絞る
- 週次の整合性検証フロー(5-4)で、列ごとの値の分布を集計して異常値を検出する

列ごとに厳密な値域が必要になった時点で、区分マスタに区分種別を追加して
複合代替キー(`区分種別 + 区分コード`)へ移行する。移行は列の再作成を伴うため、
**必要になる可能性が少しでもあるなら最初から複合キーにしておくほうが安い**。

### 7. 初期ロードと定常同期でハッシュ計算が食い違う罠

Power Query で計算したハッシュと Office Script で計算したハッシュは、
日付フォーマット・数値の丸め・空白の扱いのわずかな差で**必ず食い違う**。
一致させようとせず、6-1 Step 2 の「archiveはハッシュ空、currentは初回同期で埋める」方式にする。

### 8. タイムゾーン設定は後から変えられない

`受注日` `納期` を「日付と時刻」型で作ってしまうと、後から「日付のみ」に変更できない。
テーブルを作り直すことになる。**列を作る瞬間に決める。**

### 9. ポーリングトリガー自体がリクエストを消費する

Premium では最小間隔が1分になるが、**1分間隔にすると1フローあたり1,440件/日**を消費する。
40,000 に対しては軽いが、無意味な消費であることに変わりはない。
「即時性」の要件を確認し、15分で足りるなら15分にする。

### 10. Excel Online コネクタのファイルサイズ上限

500行×59列そのものは軽いが、条件付き書式・入力規則・過去の書式残骸が積もると数MBになる。
上限(約25MB)に近づくと予告なくエラーになる。
定期的に「未使用範囲のクリア」(Ctrl+End が最終行を大きく超えていないか)を確認する。

### 11. 200ファイル構造そのものが根本的な負債

最新月しか更新しないなら、過去200ファイルをDataverseに入れる目的は「過去参照」だけ。
参照だけなら Dataverse化は過剰かもしれない(→ 代替案B)。
**Premium のライセンス費用を払う理由を説明できるかどうかが、この問いの答えになる。**

## 10. 代替案

**Power Automate Premium の決裁が取れない場合、代替案A が第一候補になる。**
Dataverse for Teams が廃止される以上、「Business Standard の範囲で関係データを持つ」手段は
SharePoint リストしか残らない。

### 代替案A — SharePoint リストを本体にする【Premium 不可の場合の第一候補】

- 同じ標準コネクタ、フロー構造(技法1〜4)はそのまま流用できる
- 上限 3,000万アイテム。容量は SharePoint 側(Business Standard で 1TB + 10GB×ユーザー数)
- 一意制約・ルックアップ・インデックス列は持てる
- **弱点**: 5,000アイテムのリスト表示しきい値(インデックス設計で回避可能)、型が弱い、 代替キーによるUpsertが無い(GUID辞書技法は同じく使えるので実害は小さい)
- **標準コネクタのみで動くため、Business Standard with Copilot の範囲に収まる(追加費用ゼロ)**
- Excel 側の改修と Office Script は**そのまま流用できる**。切り替えが必要なのは
  フロー後半の Dataverse アクション(作成/更新/削除)を SharePoint アクションに差し替える部分だけ
- **弱点の補足**: 列レベルセキュリティが無いため `原価` `粗利益` を隠せない。
  バックアップはごみ箱(既定93日)に依存し、Dataverse のような時点復元はできない

### 代替案B — Dataverse化せず、Power Query で参照する

- 200ファイルを SharePoint に置くだけ。同期処理を一切作らない
- Excel の Power Query「SharePointフォルダーから」で200ファイルを結合し、ピボットで分析
- **同期障害ゼロ、追加コストゼロ、今日から実行可能**
- **弱点**: 書き込み不可、モバイル/アプリ化不可、10万行の結合更新に数分かかる
- **目的が集計・分析だけなら、これが最善。** Premium のライセンス費用を払う前に必ず検討すべき

### 代替案C — ローカル Access に統合DBを作る

- Microsoft 365 Business Standard には **Access(Windows PC向け)が含まれる**
- 200ファイルをリンクテーブル/インポートで統合、SQLで自由に集計。10万行は瞬時
- **弱点**: 共有・同時実行に弱い、クラウドではない、モバイル不可
- **単独PCでの分析用途なら、圧倒的に速く・安く・壊れにくい**

### 代替案D — Excel側を集約する(代替案というより、やるべき前処理)

- 200ファイル → 年次12ファイル、または「最新月 + アーカイブ1ファイル」に集約
- スキャン対象・保守対象・初期ロードの手間がすべて激減する
