# 毎月DB(Excel) → Dataverse 引合検索システム 設計書

対象: ローカルPC(Windows 11)上の Excel「毎月DB」を Dataverse に取り込み、
新規引合が来たときに過去の類似実績を検索する。

> **第2版。** 初版は Dataverse for Teams + Power Automate クラウドフローを前提としていたが、
> 以下の2点により全面的に見直した。
>
> 1. **Dataverse for Teams の廃止決定**(2027-10-30 撤去)により本格版 Dataverse へ移行
> 2. **用途が「引合検索」と確定**したことで、同期の即時性が不要になり、
>    Power Automate クラウドフローではなく **Dataflow** が適切と判明した
>
> この変更により、必要なライセンスが **Power Automate Premium → Power Apps** に変わり、
> 実装量が大幅に減った。差分は 11章を参照。

---

## 0. 前提条件

### 0-1. 目的と利用者【確定】

| 項目 | 内容 |
|---|---|
| **目的** | 新規引合が来たとき、**過去の類似実績を検索**して見積の根拠にする |
| **利用者** | 1〜3人。**最初は1人で試験運用** |
| **操作** | 読み取り専用の検索のみ。データの書き換えは行わない |
| **検索の例** | 「SUS304 20A のボールバルブを ABC商事 に、過去いくらで売ったか」 |

この目的から導かれる設計方針が3つある。**以降の設計はすべてこれに従う。**

| 方針 | 理由 |
|---|---|
| **即時同期は不要。日次バッチでよい** | 引合の見積に、昨日時点のデータで支障はない |
| **過去データ(200ファイル)こそが本体** | 検索対象は過去実績。最新月は相対的に重要度が低い |
| **全行を対象とした部分一致検索が必須** | 「SUS304 を含む」で10万行すべてを検索できること。これが要件の核心 |

### 0-2. 業務前提【ヒアリング確定済み・再質問不要】

| 項目 | 確定内容 |
|---|---|
| 行の一意キー | **受注No + 手配票No + sub_no** |
| 同期キーの形式 | 3要素を**区切り無しで連結**。`13524` + `R08-0234` + `01` → `13524R08-023401` |
| 明細行番 | **業務システムから出力不可**。取り込み時に出現順で自動採番する |
| sub_no の採番単位 | **受注No + 手配票No** ごと |
| 更新されるファイル | **最新月の1ファイルのみ**。過去200ファイルは確定・不変 |
| 削除の扱い | 物理削除 |
| ファイルの行順 | **変わらない**(並べ替えは発生しない) |
| 受注No の月跨ぎ | **発生しない** |
| 1グループの明細数 | **99以下**(sub_no は2桁で足りる) |
| 区分表 | **5行のマスタ1本で7つの区分列すべてを賄える** |
| 手配票No の空欄 | **存在しない** |
| 列名の変更 | Excel列「摘要」→「**手配票No**」、論理名 `crfff_RNo` |

### 0-3. ライセンス要件【第2版で変更】

**必要なのは Power Apps のライセンスであり、Power Automate Premium は不要。**

| 対象 | 必要なライセンス |
|---|---|
| Microsoft 365 | **Business Standard**(現行のまま。Copilot は不要) |
| Dataflow を所有するアカウント | **Power Apps**(Premium または per app) |
| 検索アプリの利用者 1〜3人 | **Power Apps**(Premium または per app) |
| ~~Power Automate Premium~~ | **不要** |

根拠は Microsoft の公式ドキュメント。

> Power Platform 環境でデータフローを作成するには、
> **Power Apps Premium、Power Apps Per User (P1)、または Power Apps Per App (P2) が必要**。

Dataflow は Power Automate のフローではなく **Power Platform のデータ統合機能**であるため、
Power Automate のライセンス体系（「アプリのコンテキスト内」制約を含む）が適用されない。

#### プラン別のコスト

| プラン | 単価(US定価の目安) | 3人分 | 備考 |
|---|---|---|---|
| **Power Apps per app** | $5 / ユーザー / アプリ | **$15 / 月** | **新規販売終了の可能性あり。要確認** |
| Power Apps Premium | $20 / ユーザー | $60 / 月 | 確実に購入できる |
| Power Apps pay-as-you-go | $10 / アクティブユーザー | 最大 $30 / 月 | **Azure サブスクリプションが別途必要** |

> **着手前の必須確認**: per app プランは 2026年1月頃に新規販売を終了したとの情報と、
> 現在も $5 で提供されているとの情報が食い違っている。
> **年額で $540 の差**になるため、リセラーまたは Microsoft に1件問い合わせること。

#### モデル駆動アプリは常にプレミアム扱い

モデル駆動アプリは Dataverse 上で動くため、**Microsoft 365 付帯ライセンスでは作ることも使うこともできない**。
ここに選択の余地はない。per app か Premium のいずれかが、作る人と使う人の全員に必要。

### 0-4. 確認済み事項

| 項目 | 確認結果 |
|---|---|
| 区分表(5行2列)が7つの区分列すべてを賄えるか | **賄える。マスタ1本で足りる** |
| `手配票No` に空欄の行があるか | **存在しない** |
| Dataverse for Teams の廃止 | 作成停止 2026-11-15 / 停止 2027-09-15 / 撤去 2027-10-30 |

### 0-5. 未確定・要確認事項

| # | 項目 | 緊急度 | 必要な理由 |
|---|---|---|---|
| 1 | **Power Apps per app プランが購入可能か** | 高 | 年 $540 の差 |
| 2 | **Dataverse の空き容量**(Power Platform 管理センター → リソース → 容量) | 高 | 本設計は 200〜250MB を消費。per app は +50MB/ライセンスしか増えない |
| 3 | 最新月ファイルの切替タイミング(締め日) | 中 | 月次のファイル配置運用に影響 |
| 4 | `受注数` `箱数` `入数` に小数が入るか | 中 | 整数型 vs 10進数型の判断 |
| 5 | モバイルから使うか | 低 | 使うならモデル駆動アプリのモバイル設定が必要 |

## 1. 全体構成

```
[ローカルPC Windows 11]
  毎月DB_2026-11.xlsx     ← 最新月。随時更新される
  archive/                ← 確定済み 200ファイル
  区分表.xlsx
        │ OneDrive 同期クライアント（Business Standard に含まれる）
        ▼
[SharePoint ドキュメントライブラリ]
  /毎月DB/current/   /毎月DB/archive/   /毎月DB/master/
        │ Dataflow（Power Query・日次 02:00）
        ▼
[Dataverse 運用環境]
  毎月DB実績テーブル（100,000行＋年6,000行）
  区分マスタ（5行）
        │
        ▼
[モデル駆動アプリ「引合検索」]  ← 1〜3人が検索
  Dataverse 検索（全文）＋ ビュー
```

### 構成の要点

| 要素 | 選択 | 理由 |
|---|---|---|
| ローカル → クラウド | **OneDrive 同期クライアント** | PCがオフラインでもクラウド側がファイルを保持する。ゲートウェイは不要 |
| 取り込み | **Dataflow** | Power Query で動き、Upsert と削除検出が標準機能。Power Automate ライセンス不要 |
| 更新頻度 | **日次 1回** | 引合検索に即時性は不要(0-1) |
| 検索UI | **モデル駆動アプリ** | **キャンバスアプリは委任制限で全行検索できない**(5-1) |
| 検索方式 | **Dataverse 検索** + ビュー | 複数列を横断した全文検索 |

## 2. Excel側に必要な改修

**第2版では要件が大幅に減った。** Power Query はワークシートを直接読めるため、
初版で必須としていた**テーブル(ListObject)化は不要**になった。

### 2-1. コード系列の書式を「文字列」にする【必須】

```
受注No / 手配票No / 商品コード / 得意先コード / 担当者コード
部門コード / 直送先コード / 見積No / 番船 / ﾌﾟﾛｼﾞｪｸﾄ名コード
```

数値書式のままだと `0001` → `1` になりキーが壊れる。
**`受注No` と `手配票No` は同期キーの構成要素**なので、ここが崩れると取り込み全体が破綻する。

### 2-2. ファイル配置とファイル名規約

```
SharePoint: /毎月DB/
    current/  毎月DB_2026-11.xlsx     ← 最新月
    archive/  毎月DB_2026-10.xlsx     ← 確定済み
              ... (200ファイル)
    master/   区分表.xlsx
```

- 月次締めで `current/` のファイルを `archive/` へ移動し、新しい月のファイルを `current/` に置く
- OneDrive の一時ファイル `~$*.xlsx` と競合コピー `*-<PC名>.xlsx` は Power Query 側で除外する

### 2-3. アーカイブの集約【強く推奨】

200ファイルを毎回読むと、Dataflow の更新に数十分かかる。
**年次12ファイル(または1ファイル)に集約**すると、更新が大幅に短縮される。

集約は一度きりの作業で、Power Query で結合して出力するだけ。**構築の最初にやる価値がある。**

### 2-4. 不要になったもの

| 初版の要件 | 第2版 |
|---|---|
| 全ファイルのテーブル化(`T_DB`) | **不要**。Power Query はシートを直接読む |
| `ensureTable()` による自動テーブル化 | **不要** |
| Office Script(334行) | **不要**。Power Query が同等の処理を行う |

## 3. Dataverse テーブル設計

### 3-1. テーブル一覧

| テーブル | 論理名 | 用途 | 想定行数 |
|---|---|---|---|
| 毎月DB実績 | `crfff_jisseki` | 本体 | 100,000 → +6,000/年 |
| 区分マスタ | `crfff_kubun` | 区分表(5行2列) | 5 |

> `crfff_` は発行者プレフィックスの仮置き。本格版 Dataverse では**ソリューションの発行者を自分で定義できる**ため、
> `nlm_` のような意味のある接頭辞を最初に決めること。**後から変更すると全列の再作成になる。**

初版にあった `同期制御` `同期エラー` テーブルは**不要**。
Dataflow が更新履歴とエラーを自前で保持し、失敗時はオーナーに通知される。

### 3-2. 管理列

| 表示名 | 論理名 | 型 | 備考 |
|---|---|---|---|
| 同期キー | `crfff_sync_key` | テキスト(100) | **主名前列 かつ 代替キー**。Upsert の判定に使う |
| 受注No | `crfff_order_no` | テキスト(30) | キー構成要素 |
| 手配票No | `crfff_RNo` | テキスト(30) | キー構成要素。旧「摘要」列 |
| 明細枝番 | `crfff_sub_no` | 整数 | キー構成要素。取り込み時に採番 |
| ソースファイル | `crfff_source_file` | テキスト(100) | `毎月DB_2026-11.xlsx` |

初版にあった `行ハッシュ` `最終同期日時` は**不要**。差分判定は Dataflow が行う。

> **論理名の大文字小文字に注意。**
> Dataverse の論理名は**常に小文字に正規化される**。
> スキーマ名に `crfff_RNo` と入力しても、実際の論理名は **`crfff_rno`** になる。

### 3-4. 区分列はルックアップではなくテキストにする【第2版で変更】

初版では区分列7本を**区分マスタへのルックアップ**にしていた。第2版では**テキスト列**に変更する。

| | ルックアップ(初版) | **テキスト(第2版)** |
|---|---|---|
| Dataflow でのマッピング | 代替キーによる解決が必要。設定が煩雑 | **単純な値のコピー** |
| コードがマスタに無い場合 | **行の作成が失敗する** | 取り込まれる |
| 検索 | 間接参照になり扱いにくい | **そのまま検索対象になる** |
| 参照整合性 | 効く | 効かない |

**用途が検索である以上、参照整合性より取り込みの確実性と検索のしやすさを優先する。**
区分名を表示したい場合は、区分マスタを別テーブルとして残し、モデル駆動アプリ側で参照する。

初版で懸念した「区分コードが空だと404で行の作成が失敗する」問題も、テキスト化により消滅する。

> 将来、区分による絞り込みドロップダウンや参照整合性が必要になった時点でルックアップ化できる。
> 列の型変更は再作成を伴うが、検索用途で先にルックアップを作る理由は無い。

### 3-5. 型選択の根拠【間違えると後戻りできない】

| 項目 | 正解 | 間違えるとどうなるか |
|---|---|---|
| `受注日` `納期` | **日付のみ / タイムゾーン非依存** | UTC保存により JST で1日ズレる。**後から変更不可。テーブル作り直し** |
| 金額列 | **10進数**(通貨型を使わない) | `_base` 列が自動生成され、列数と容量が実質2倍になる |
| 監査(Auditing) | **OFF** | 更新のたびに監査ログが増え、本体データを上回る |
| コード列 | **テキスト**(数値にしない) | 先行ゼロが落ちてキーが壊れる |

### 3-6. 検索インデックス【第2版で追加・必須】

**検索対象列には必ずインデックスを設定する。** 10万行の検索性能に直結する。

```
crfff_item_code       商品コード
crfff_spec_model      規格・型番
crfff_item_name       商品名
crfff_customer_code   得意先コード
crfff_customer_name1  得意先名１
crfff_order_date      受注日（並べ替え用）
crfff_source_file     ソースファイル
```

### 3-7. 容量見積り

| 内訳 | 1行あたり |
|---|---|
| テキスト列 42本 × 平均12文字 × 2byte | 約 1,000 B |
| 数値・日付列 17本 × 8byte | 約 136 B |
| Dataverse システム列オーバーヘッド | 約 800〜1,000 B |
| **計** | **約 2.0〜2.5 KB** |

- 100,000行 → **200〜250 MB**
- 年間増加 6,000行 → **約 15 MB/年**

容量はテナント単位のプール。付与元は以下。

| 付与元 | Dataverse Database 容量 |
|---|---|
| テナント既定容量(最初の Power Apps / Power Automate ライセンス購入時) | 一般に 10 GB |
| Power Apps Premium 1ライセンスあたり | + 250 MB |
| **Power Apps per app 1ライセンスあたり** | **+ 50 MB** |

> **per app を選ぶ場合は要注意。** 3ライセンスでも +150MB しか増えず、本設計の消費(200〜250MB)に届かない。
> **テナント既定容量が使える前提かどうかを、着手前に Power Platform 管理センターで必ず確認すること**(0-5 の #2)。

## 4. Dataflow 設計

### 4-1. 全体方針

| 項目 | 設定 |
|---|---|
| 種類 | 標準データフロー(Dataverse にデータを格納) |
| ソース | SharePoint フォルダー(`/毎月DB/`) |
| 対象テーブル | `crfff_jisseki`(既存テーブルに読み込む) |
| キー | **代替キー `crfff_sync_key`** による Upsert |
| 削除 | **「クエリ出力に存在しない行を削除する」を有効化** |
| 更新スケジュール | **毎日 02:00**(1日1回) |
| 所有者 | 専用アカウント(Power Apps ライセンス付き) |

### 4-2. Power Query の処理手順

```
1. SharePoint フォルダーに接続（サイトURL を指定）
2. 一時ファイル・競合コピーを除外
3. Excel ブックを展開し、ワークシートを取得
4. ヘッダーを昇格し、不要な行を除去
5. 列名を論理名に変更（59列）
6. 型を変換（日付・10進数・テキスト）
7. 受注No + 手配票No ごとに出現順で sub_no を採番
8. sync_key を生成
9. Dataverse にマッピングして読み込む
```

### 4-3. 主要な M コード

#### ファイルの絞り込み

```m
// OneDrive の一時ファイルと競合コピーを除外する
FilteredFiles = Table.SelectRows(Source, each
    not Text.StartsWith([Name], "~$")
    and Text.EndsWith([Name], ".xlsx")
    and not Text.Contains([Name], "-DESKTOP-")
)
```

#### ワークシートの展開

```m
// テーブル(ListObject)ではなくワークシートを直接読む
Workbooks   = Table.AddColumn(FilteredFiles, "Data", each Excel.Workbook([Content])),
Expanded    = Table.ExpandTableColumn(Workbooks, "Data", {"Name","Kind","Data"},
                                      {"SheetName","Kind","SheetData"}),
SheetsOnly  = Table.SelectRows(Expanded, each [Kind] = "Sheet"),
```

> **`Kind = "Sheet"` が重要。** 初版の `Kind = "Table"` だと、
> テーブル化していないファイルが読み飛ばされる。

#### sub_no の採番（受注No + 手配票No 単位の出現順）

```m
// Table.Group はグループ内の元の行順を保持するため、
// インデックスがそのまま「出現順」になる
Grouped = Table.Group(
    Typed,
    {"crfff_order_no", "crfff_RNo"},
    {{"g", each Table.AddIndexColumn(_, "crfff_sub_no", 1, 1, Int64.Type), type table}}
),

ExpandedSubNo = Table.ExpandTableColumn(
    Grouped, "g",
    List.RemoveItems(Table.ColumnNames(Typed), {"crfff_order_no", "crfff_RNo"})
        & {"crfff_sub_no"}
),
```

#### sync_key の生成

```m
// 3要素を区切り無しで連結する  例: 13524 + R08-0234 + 01 → 13524R08-023401
AddedSyncKey = Table.AddColumn(ExpandedSubNo, "crfff_sync_key",
    each [crfff_order_no]
       & [crfff_RNo]
       & Text.PadStart(Text.From([crfff_sub_no]), 2, "0"),
    type text
),
```

#### キー欠損の検出（取り込みを止める）

```m
// キーが空の行があれば、その場で更新を失敗させる。
// 静かに取り込んで後から気づく事態を防ぐ。
Validated = Table.AddColumn(AddedSyncKey, "_check", each
    if [crfff_order_no] = null or Text.Trim([crfff_order_no]) = "" then
        error "受注Noが空の行があります: " & [crfff_source_file]
    else if [crfff_RNo] = null or Text.Trim([crfff_RNo]) = "" then
        error "手配票Noが空の行があります: " & [crfff_source_file]
    else true),

Cleaned = Table.RemoveColumns(Validated, {"_check"}),
```

#### 同期キーの重複検出

```m
// 受注No と 手配票No を区切り無しで連結しているため、
// 桁数の組み合わせによっては別の行と同じ文字列になりうる。
// 代替キーの一意制約でも検知されるが、ここで止めたほうが原因が分かりやすい。
DupCheck = if Table.RowCount(Table.Distinct(Cleaned, {"crfff_sync_key"}))
            <> Table.RowCount(Cleaned)
           then error "同期キーが重複しています"
           else Cleaned,
```

### 4-4. 日付と数値の扱い

| 列 | 変換 | 注意 |
|---|---|---|
| `受注日` `納期` | **Date 型**(DateTime ではない) | DateTime にすると Dataverse 側でタイムゾーン変換が入りズレる |
| 金額・数量列 | Decimal 型 | — |
| コード列 | **Text 型を明示** | 自動型検出に任せると先行ゼロが落ちる |

> **Power Query の自動型検出は無効にすること。**
> `オプション` → `現在のブック` → `データの読み込み` → 「列タイプを自動検出しない」。
> 有効のままだと、ファイルによって型が揺れて取り込みが失敗する。

### 4-5. Dataverse へのマッピング

読み込み先の設定画面で以下を指定する。

| 設定 | 値 |
|---|---|
| 読み込み設定 | **既存のテーブルに読み込む** |
| 対象テーブル | `crfff_jisseki` |
| 代替キー | **`crfff_sync_key`** |
| 列マッピング | 論理名どおり1対1(手順5で改名済みのため自動一致する) |
| 「クエリ出力に存在しない行を削除する」 | **有効** |

> **削除検出は更新時間を延ばす。** 毎回10万行の突合が発生するため。
> アーカイブを集約(2-3)しておくと体感が大きく変わる。

### 4-6. 更新スケジュールと監視

```
毎日 02:00 に自動更新
```

更新に失敗すると、**Dataflow の所有者にメール通知**が届く。
初版で設計した同期エラーテーブルと Teams 通知フローは不要。

月次の運用は次の2つだけ。

```
1. 前月のファイルを current/ → archive/ へ移動
2. 新しい月のファイルを current/ に配置
```

ファイル名規約(2-2)に従っていれば、Dataflow 側の設定変更は不要。

## 5. 検索アプリ設計

### 5-1. キャンバスアプリを使わない【最重要】

**Power Apps のキャンバスアプリでは、10万行の部分一致検索ができない。**

キャンバスアプリには**委任(delegation)** の仕組みがあり、サーバー側で処理できないクエリは
**先頭500件(設定で最大2,000件)しか取得しない**。

| 関数 | Dataverse に対して委任されるか |
|---|---|
| `StartsWith` / `EndsWith` | される |
| **`Contains`(部分一致)** | **されない** |
| **`Search()`** | **されない** |

> 上限を 2,000 に引き上げても、**非委任のクエリがテーブル全体を検索するようにはならない**。
> ローカルで処理できる件数が増えるだけ。

引合検索では `規格・型番` が「ボールバルブ SUS304 20A」のような形になるため、
前方一致では実用にならず、**部分一致が必須**。したがってキャンバスアプリは要件を満たさない。

### 5-2. モデル駆動アプリ + Dataverse 検索

モデル駆動アプリのビューは FetchXML で動くため、**委任制限が無く全行が対象になる**。

#### 構築手順

```
1. Power Platform 管理センターで Dataverse 検索を有効化
     環境 → 設定 → 製品 → 機能 → Dataverse search → オン

2. 検索対象列を「クイック検索ビュー」に登録
     商品コード / 規格・型番 / 商品名 / 得意先名１ / 得意先コード

3. 既定のビューを作成
     列: 受注日 / 得意先名１ / 商品コード / 商品名 / 規格・型番 / ｻｲｽﾞ /
         受注数 / 単価 / 売単価 / 原価 / 粗利益 / 納期 / 受注No / 手配票No
     並べ替え: 受注日 降順

4. モデル駆動アプリを新規作成し、毎月DB実績テーブルを追加

5. 1〜3人に共有（各自に Power Apps ライセンスが必要）
```

**コードは1行も書かない。半日程度の設定作業で完成する。**

#### Dataverse 検索の利点

| | Excel のテキストフィルター | **Dataverse 検索** |
|---|---|---|
| 全行の部分一致 | できる | できる |
| **複数列を横断して一度に検索** | できない(列ごとに指定) | **できる** |
| **表記ゆれ・語の分割** | できない | **できる**(全文検索エンジン) |
| 検索速度(10万行) | 数秒 | 瞬時 |
| モバイル | 不可 | 可 |

「商品コードでも規格でも商品名でも、どこかに SUS304 が入っていれば拾いたい」
という検索ができる点が、Excel に対する明確な優位性になる。

### 5-3. 検索の実際の操作

引合「SUS304 20A ボールバルブ / ABC商事」が来た場合。

```
1. アプリ上部の検索ボックスに "SUS304" と入力
     → 商品コード・規格・型番・商品名を横断して該当行が出る
2. ビューの列フィルターで 得意先名１ を "ABC" で絞る
3. 受注日 降順で並んでいるため、直近の実績が最上段に出る
4. 単価 / 売単価 / 原価 / 粗利益 を確認して見積に使う
```

## 7. 見落としやすい弱点

重要度順。

### 1. ライセンスとDataverse容量を確認せずに着手すること

per app が購入できるかで**年 $540**、テナント既定容量が使えるかで**設計の可否**が変わる(0-5)。
テーブルを作る前に両方を確認すること。

### 2. キャンバスアプリで作ってしまうこと

最も踏みやすい地雷。Power Apps の既定の作り方がキャンバスアプリであるため、
何も考えずに作ると**先頭2,000行しか検索しないアプリ**ができあがる。
しかも**動いているように見える**ため、気づくのが遅れる。**必ずモデル駆動アプリで作ること**(5-1)。

### 3. Dataflow の所有者を個人アカウントにすること

所有者の異動・退職・パスワード変更で更新が無言で止まる。
**専用アカウントを用意し、そこに Power Apps ライセンスを割り当てる**こと。

### 4. タイムゾーン設定は後から変えられない

`受注日` `納期` を「日付と時刻」型で作ると、後から「日付のみ」に変更できない。
テーブルを作り直すことになる。**列を作る瞬間に決める。**

### 5. 自動型検出による取り込みの揺れ

Power Query の自動型検出を有効のままにすると、ファイルによって列の型が変わり、
ある月だけ取り込みが失敗する。**必ず無効化し、型を明示すること**(4-4)。

### 6. アーカイブ200ファイルによる更新時間

削除検出と200ファイルの結合が重なると、更新が数十分になる。
**年次12ファイルへの集約**(2-3)を構築時にやっておくこと。

### 7. 200ファイル構造そのもの

最新月しか更新しないのに、ファイルが200個ある状態は保守負債。
集約は検索システムのためだけでなく、業務運用としても整理の価値がある。

## 8. 代替案

### 代替案A — Excel + Power Query(追加費用ゼロ)

Dataverse を使わず、Excel のブックで完結させる。

```
Excel ブック
 └ Power Query で archive の200ファイルを結合
    └ データモデルに読み込む
       └ テキストフィルター(指定の値を含む)で検索
```

| | 本設計(Dataverse) | **代替案A(Excel)** |
|---|---|---|
| 月額 | $15〜$60 | **$0** |
| 全行の部分一致検索 | できる | **できる**(テキストフィルター) |
| 複数列の横断検索 | できる | **できない**(列ごとに指定) |
| 表記ゆれ | 強い | 弱い |
| モバイル | 可 | 不可 |
| 更新 | 自動(日次) | **デスクトップ版 Excel で手動**(月1回) |
| 構築時間 | 1〜2日 | **半日** |

> **「列を指定した部分一致で足りる」なら、代替案Aで要件を満たす。**
> 本設計を選ぶ判断材料は、**横断的な全文検索・表記ゆれ耐性・モバイル**の3点に絞られる。
>
> 費用ゼロ・半日で試せるため、**本設計に着手する前に代替案Aを作って検証することを推奨する。**
> 作った Power Query は本設計の Dataflow にそのまま流用できるため、無駄にならない。

### 代替案B — SharePoint リスト

Dataverse ではなく SharePoint リストに取り込む。標準コネクタのみで動くため追加費用ゼロ。
ただし Dataflow は使えず Power Automate が必要になり、全文検索も Dataverse 検索ほど強くない。
**本用途では代替案A のほうが素直。**

### 代替案C — ローカル Access

Business Standard に Access が含まれる。10万行は瞬時。単独PCでの利用なら最速・最安。
共有・モバイルは不可。
