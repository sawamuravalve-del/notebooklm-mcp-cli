0-3ローカルPC → クラウドの経路

Power Automate のクラウドフローはローカルファイルを直接読めない。

Power Automate Premium を取得するとオンプレミスデータゲートウェイ + File System コネクタが 使えるようになり、ローカルファイルを直接読む選択肢が増える。ただし本設計では採用しない。

方式評価
OneDrive 同期クライアント → SharePoint(採用)PCがオフラインでも、同期済みのファイルをクラウド側が常に保持している。Excel Online コネクタと Office Script がそのまま使える

1-1明細行番は Office Script が出現順で自動採番する 方針確定

現行59列に、1伝票内の明細を識別する列が無い。業務システムからの出力も不可であることが確認された。 このため Excel には列を追加せず、Office Script が読み取り時に採番する。

受注No | 手配票No | sub_no | sync_key
13524  | R08-0234 | 01     | 13524R08-023401
13524  | R08-0234 | 02     | 13524R08-023402
13524  | R08-0235 | 01     | 13524R08-023501   ← 手配票No ごとに独立採番
13600  | R08-0234 | 01     | 13600R08-023401

採番は「ファイルの上から出てきた順」。実装は sync-read-script.ts の main() 内 counter を参照。

この方式が成立する前提(すべて確認済み)

前提成立しないと何が起きるか
ファイルの行順が変わらない並べ替えると sub_no が入れ替わり、内容が同じでも全行が更新扱いになる(最大500更新=514リクエスト)
同一の受注No が複数の月ファイルに出現しない同期キーが月をまたいで衝突する。ただし代替キーの一意制約で「新しい行の追加」が失敗するため、無言のデータ破壊にはならず検知できる
明細数が99以下桁あふれ。スクリプトが例外で停止する(MAX_LINES_PER_GROUP)

残る注意点: 行がグループの途中に挿入されると、それ以降の sub_no がズレる (末尾への追加なら影響なし)。前提上は発生しないが、万一発生した場合は 最終状態は正しくなるものの delete + create が走り、Dataverse 行の createdon が失われる。 週次の整合性検証フロー(5-4)で削除件数を監視すること。

将来この前提が崩れた場合の対処: Office Script は書き込みも可能なため、 採番結果を Excel の列に書き戻して永続化すれば、行順・挿入の双方から独立した 真に安定したキーになる。10行程度の追加で実装できる。

1-2テーブル(ListObject)化

Excel Online (Business) コネクタはセル範囲を読めない。テーブルだけを読む。

  • 全ファイルで同じテーブル名にする(例: T_DB)。ファイルごとに名前が違うとフローが分岐地獄になる
  • テーブル名を後から変えると全フローが即死する。命名は最初に固定する
  • ヘッダー行は1行のみ。結合セル・空列・重複列名は不可

1-3コード系列の書式を「文字列」にする

受注No 手配票No 商品コード 得意先コード 担当者コード 部門コード 直送先コード 見積No 番船

数値書式のままだと 0001 → 1 になり、Dataverse側のキーが壊れる。 受注No と 手配票No は同期キーの構成要素なので、ここが崩れると同期そのものが破綻する。 既に壊れている過去データがあるなら、初期ロード前に一括修正する。

Dataverse for Teams 時代の 6,000 件から 6.6 倍になった。ただし以降の節で述べる技法1〜4はそのまま残す。 余裕ができたから雑に作ってよい、という話にはならない。理由は3つ。

  1. Dataverse のサービス保護制限(5分あたり6,000)はライセンスと無関係に効く。 結局ループは絞る必要がある
  2. 実変更量に比例する設計のほうが、障害時の復旧と原因特定が速い。 500行保存して3行しか書かない設計なら、ログに出る書き込みが常に「実際に起きた変更」と一致する
  3. Premium を手放す判断が将来あっても、設計を作り直さずに済む

2-2素直に作ると破綻する

500行を Apply to each で回し、中で「Dataverseから行を検索」→「条件分岐」→「作成 or 更新」とすると、 1行あたり3〜5リクエスト → 500行で1,500〜2,500件。さらに区分列7本をルックアップで解決すると +3,500件/500行。 40,000 の予算なら一見収まるが、Dataverse のサービス保護制限(5分あたり6,000)に先にぶつかって 429 が多発する。 リクエスト予算ではなくスループットの問題として、ループは絞る必要がある。

2-3リクエストを最小化する技法

これが本設計の核心。「ループの中に置くDataverseアクションを1個だけにする」ことが目標。 技法1〜4は Premium の有無にかかわらず有効で、代替案A(SharePoint リスト)にもそのまま流用できる。

技法1: 配列操作アクションは件数に関係なく1リクエスト

アイテムの選択(Select) 配列のフィルター処理(Filter array) 作成(Compose) 結合(Join) は、 配列が500件でも1回の実行で1リクエスト。差分計算をすべてこれで行う。

技法2: JSONオブジェクトを辞書として使い、O(1)ルックアップを実現

Power Automate の式には filter() が無い。そのため「このキーに対応するDataverseのGUIDは?」を ループ内で引こうとすると Filter array を回すことになり +1リクエスト/行。

これを回避する。Dataverseから取得した配列を、キー→値のJSONオブジェクト(辞書)に変換する。

[1] アイテムの選択 「Select_GUID」
    差し込み元: outputs('Dataverse行の一覧')?['body/value']
    マップ(テキストモード):
      concat('"', item()?['crfff_sync_key'], '":"', item()?['crfff_meisaiid'], '"')

[2] 作成 「GUID辞書」
    json(concat('{', join(body('Select_GUID'), ','), '}'))

[3] 参照(ループ内、追加リクエストゼロ)
    outputs('GUID辞書')?[items('更新ループ')?['sync_key']]

3アクション(=3リクエスト)で500件分の辞書ができる。同じ要領で HASH辞書 EXCELキー辞書 を作る。

キーに " や \ が含まれると JSON が壊れる。sync_key は Office Script 側で [^0-9A-Za-z\-_] を除去してサニタイズしておく。

技法3: 差分を「新規/更新/削除」の3配列に事前分割する

ループ内に条件分岐を置くと、分岐アクション自体が1リクエスト/行。 分割を Filter array 3個(=3リクエスト)で済ませ、ループ内はDataverseアクション1個だけにする。

新規 = Filter(Excel行, @equals(outputs('GUID辞書')?[item()?['sync_key']], null))

更新 = Filter(Excel行, @and(
          not(equals(outputs('GUID辞書')?[item()?['sync_key']], null)),
          not(equals(outputs('HASH辞書')?[item()?['sync_key']], item()?['row_hash']))))

削除 = Filter(Dataverse行, @equals(outputs('EXCELキー辞書')?[item()?['crfff_sync_key']], null))

技法4: 行ハッシュで「実際に変わった行」だけ書く

Excelの保存操作は全行を等しく「更新されたかもしれない行」にしてしまう。 59列を連結したハッシュを行ごとに持ち、Dataverse側の値と一致する行は一切書かない。

Power Automate の式には sha256() などのハッシュ関数が無い。 連結文字列をそのまま保存する手もあるが、備考 が長いと数千文字になり容量を食う。

→ Office Script 内で FNV-1a を計算し、16桁の16進文字列にする(後述)。

技法5: OData $batch で書き込みを一括化する Premium で新たに可能

Power Automate Premium では HTTP with Microsoft Entra ID コネクタが使える。 Dataverse Web API の $batch エンドポイントに複数の操作をまとめて送れる。

POST https://<org>.crm7.dynamics.com/api/data/v9.2/$batch
Content-Type: multipart/mixed; boundary=batch_sync

--batch_sync
Content-Type: multipart/mixed; boundary=changeset_1

--changeset_1
Content-Type: application/http
Content-Transfer-Encoding: binary

POST /api/data/v9.2/crfff_meisais HTTP/1.1
Content-Type: application/json

{"crfff_sync_key":"13524R08-023401", "crfff_order_no":"13524", ...}
--changeset_1
  (以下、操作を繰り返す)
--changeset_1--
--batch_sync--

Power Platform リクエストとしては HTTP アクション1回 = 1件。 500行の書き込みが 500リクエスト → 数リクエストになる。

ただし、最初からこれを使うことは推奨しない。 理由は3つ。

  1. サービス保護制限はバッチの中の操作数で評価される。 1バッチあたり100〜200操作に抑える必要があり、 「1リクエストで何でも入る」わけではない
  2. changeset 内はトランザクション。 1件失敗すると全体がロールバックするため、 どの行が原因かの特定が難しくなる。500行のうち1行だけ日付が壊れていた、という状況で切り分けできない
  3. JSON と multipart の組み立てが複雑で、フローの可読性が大きく落ちる

→ 初期ロードや月次の全入替のような大量書き込み専用の手段として持っておく。 日常の数件〜数十件の更新は、素直な Dataverse コネクタのほうが運用しやすい。 まず技法1〜4だけで運用を開始し、実測して必要になってから導入すること。

3-4型選択の根拠(ここを間違えると後戻りできない)

通貨型を使わない

金額列(原価/受注金額/粗利益/売価金額/標準価格/内税額/外税額/受注残高)は 10進数 にする。 Dataverse の通貨型を選ぶと、

  • transactioncurrencyid(通貨へのルックアップ)と exchangerate が暗黙に必要になる
  • 列ごとに _base 列(基準通貨換算値)が自動生成され、列数と容量が実質2倍になる
  • 書き込みのたびに通貨解決が走り、フローが複雑化する

単一通貨(円)しか扱わないなら通貨型は害しかない。

日付は「日付のみ / タイムゾーン非依存」

受注日 納期 を「日付と時刻」型にすると、Dataverse は UTC で保存しユーザーのタイムゾーンで表示する。 JST(+9)環境では 2026-08-04 が 2026-08-03 と表示される事故が起きる。 「日付のみ」+ 動作「タイムゾーンに依存しない」を必ず選ぶ。この設定は後から変更できない。

テキスト長を既定の100/4000のままにしない

Dataverse は実データ長で消費するが、長すぎる定義はインデックス・検索列の効率を落とす。 逆に短すぎると同期が失敗する。実データの最大長を調べて +50% 程度で設定する。

論理名は必ず小文字になる — crfff_RNo の落とし穴

Dataverse の論理名(logical name)は常に小文字に正規化される。 列作成時に表示名「手配票No」、スキーマ名 crfff_RNo と入力しても、 Web API と Power Automate の Dataverse コネクタが使う論理名は crfff_rno になる。

  • Office Script が返す JSON キーは RNo(本書の表記どおり)
  • フローで Dataverse 列に書き込む際の参照名は crfff_rno(小文字)

他の58列は元から小文字なのでこの問題は起きない。大文字を含むのは RNo だけなので、 ここだけ取り違えると「その列だけ無言で値が入らない」という切り分けの難しい障害になる。

監査(Auditing)をOFFにする

テーブルの監査をONにすると、更新のたびに監査ログ行が生成される。 毎日500行更新する運用では本体データより監査ログのほうが大きくなる。 本格版 Dataverse では 2 GB のハード上限は無いが、テナント共有の容量プールを圧迫する(3-7)。 必要なら Dataverse ではなく SharePoint リストに変更履歴を出す。

素直にやると破綻する: ルックアップ列に値を入れるには通常、対象行のGUIDが要る。 ループ内で「区分マスタから行を取得」を7回やると +3,500リクエスト/500行。

解決策 — 代替キーによる @odata.bind: Dataverse コネクタの「新しい行の追加」のルックアップ欄に、GUIDではなく 代替キー参照の文字列を直接入れる。Dataverse サーバー側で解決されるため 追加リクエストは発生しない。

/crfff_kubuns(crfff_kubun_code='01')

式にすると(Power Automate ではシングルクォートを2つ重ねてエスケープする):

concat('/crfff_kubuns(crfff_kubun_code=''', items('新規ループ')?['data_kubun'], ''')')

本格版 Dataverse では代替キーの作成に制約が無い(Teams 環境では作成可否がテナント設定に左右されていた)。 なお、フロー冒頭で区分マスタ5行を1回だけ取得し(=1リクエスト)、技法2の辞書に載せて GUID を引く方法も同じコストで済む。 代替案A(SharePoint リスト)に切り替える可能性があるなら、辞書方式のほうが移植しやすい。

区分列に空欄がある場合の扱い

区分コードが空だと /crfff_kubuns(crfff_kubun_code='') になり、該当行が無いため Dataverse が 404 を返してその行の作成が失敗する。区分列は7本あるので、 7倍の確率でこれを踏む。

対処は2つ。推奨は前者。

  1. 区分マスタに「未設定」行を1本追加する(__NONE__ / 未設定)。 Office Script 側で空を __NONE__ に寄せる。フローに分岐が不要で、 集計時に「未設定が何件あるか」が見えるという利点もある
  2. フロー側で if(empty(...), null, concat(...)) と分岐する。 7列すべてに書く必要があり、式が読みにくくなる

現時点で区分列に空欄が入るかは未確認(0-5)。入らないなら何もしなくてよい。

4Office Script(読み取り・正規化・ハッシュ生成)

Excel Online (Business) の「スクリプトの実行」は標準コネクタのアクション。 1リクエストで以下をすべて処理でき、フロー側のアクション数を劇的に減らせる。

  • テーブル T_DB が無ければ作成する(冪等。毎月の手作業が不要になる)
  • テーブル全体を読む(「行を一覧表示」の256件ページングが不要)
  • 半角カナ・日本語の列名 → ASCII論理名に正規化
  • 日付シリアル値 → ISO文字列に変換
  • 空白セル・不可視文字(ZWSP等) → null に正規化
  • 受注No + 手配票No ごとに出現順で sub_no を採番し、同期キーを生成
  • 行ハッシュ(FNV-1a 16桁hex)の生成

実装

完全なコードは sync-read-script.ts を参照。 本書には転記しない(二重管理になり、必ず片方が古くなるため)。

同ファイルは tsc による型チェックと、採番・ハッシュ・正規化・異常系を含む 動作テストを通している。Office Scripts エディタへはそのまま貼り付けられる。

  ※ 区分が空の行があるなら、空のときはルックアップ欄を null にする分岐が要る

Dataverse 行の一覧表示で select を必ず指定する理由 指定しないと59列すべてが返り、500行で数MBのペイロードになる。 辞書化に必要なのは sync_key row_hash GUID の3つだけ。転送量とタイムアウトの両方に効く。

8メリット / デメリット

メリット

  1. リレーショナルな型・一意制約・参照整合性が効く。素のExcelでは不可能な整合性担保
  2. リクエスト消費が実変更量に比例。500行保存しても変更0なら書き込み0
  3. 完全な冪等性。代替キー+ハッシュ設計により、何度流しても結果が同じ。失敗しても再実行するだけ
  4. 容量のハード上限が無くなった(2 GB/環境 → テナントプール)。履歴・ログの選択肢が戻る
  5. 列レベルセキュリティが使える。 原価 粗利益 利益率 を特定メンバーにだけ見せる運用が可能
  6. バックアップ / 復元 / 環境のコピーが使える。 本番を複製した検証環境を作れる
  7. 環境が Teams のチームから独立する。 チームを削除してもデータは消えない
  8. プラグイン / カスタム API でサーバー側のバリデーションと一括処理ができる
  9. プレミアムコネクタとオンプレミスデータゲートウェイが使え、将来の拡張余地が大きい
  10. リクエスト上限が 6,000 → 40,000。大量更新や初期ロードの現実性が上がる
  11. 最新月1ファイルのみ更新という業務特性が、この構成に理想的に噛み合う

デメリット

  1. Power Automate Premium のライセンス費用が発生する(約 $15/ユーザー/月)。前提3に抵触する
  2. 容量がテナント共有プールになり、他部署と食い合う。 2 GB の上限と引き換えに、 自分だけでは制御できない変数が増えた
  3. 運用負荷が上がる。 Power Platform 管理センター、ソリューション、DLP ポリシー、 環境のライフサイクル管理の知識が必要になる。Teams 環境は「作れば動く」だったがそうではなくなる
  4. 接続の所有者が単一障害点。 所有者の退職・パスワード変更・MFA再認証で全フローが停止する
  5. Excel Online コネクタが脆い。 テーブル名変更・ファイル移動・ファイルサイズ超過で即死
  6. OneDrive同期の遅延と競合。 PCがスリープ/オフラインだと同期されず、競合コピーが発生しうる
  7. Excel側の改修が必須(コード列の文字列書式化)。既存業務手順に影響する
  8. 障害の切り分けが5層にまたがる(Excel / OneDrive / SharePoint / Power Automate / Dataverse)

9見落としやすい弱点(率直な指摘)

重要度順。

1ライセンス未決裁のまま設計を進めるリスク — 最大の落とし穴

本格版 Dataverse は Power Automate Premium 無しでは動かない(0-2)。 Copilot を足しても解決しない。

この決裁が取れないまま Excel 側の改修や Office Script の実装を進めると、 作ったものが丸ごと使えなくなる。先に決裁を取るか、少なくとも 「取れなかった場合は代替案A(SharePoint リスト)へ切り替える」と決めてから着手すること。

代替案Aへの切り替えはフロー構造(技法1〜4)をほぼ流用できるため、 Excel 側の改修と Office Script は無駄にならない。切り替え点はDataverseコネクタの 部分だけ。この事実が分かっていれば並行して進めてよい。

2物理削除 + Excelの誤操作 = 復旧不能

以下はすべて「Excel上で行が消えたように見える」操作で、そのままDataverseの物理削除につながる。

  • オートフィルターで絞り込んだ状態のまま別ファイルとして保存した
  • 誤って行を削除して気づかず保存した
  • 前月のファイルを current/ に置いてしまった

サーキットブレーカーは必須: 1回の同期で削除対象が max(20件, 既存件数の20%) を超えたら 中断してTeamsに通知し、人間が承認するまで実行しない。実装コストは条件アクション1個(1リクエスト)。

さらに、論理削除への変更を再検討する価値が上がった。 本格版 Dataverse では容量のハード上限が無くなったため、削除フラグ列を持つコストが 実質ゼロになっている。物理削除を選ぶ積極的な理由が「Excelと完全一致させたい」だけなら、 フロー④の整合性検証で同じ目的が達成できる。

3サービスアカウントに Premium ライセンスが要る

個人アカウントでフローを作ると、その人の異動・退職・パスワード変更・MFA再認証で 全フローの接続が無効化され、同期が無言で止まる。 同期専用アカウント(例: svc-dbsync@...)を用意するのが正しい。

本格版 Dataverse では、このアカウントにも Power Automate Premium が必要になる。 Business Standard 1本では足りない。ライセンス費用を見積もる際はここを忘れないこと。

4Dataverse サービス保護制限と並列度 — 重要度が上がった

「ライセンスが 40,000 になったから並列度を上げれば速い」は誤り。

Dataverse のサービス保護制限(5分あたり6,000リクエスト / 同時接続約20)は ライセンスと無関係に効く。上げすぎると 429 が返り、リトライが発生し、 リトライもリクエストを消費するため予算が悪化する。 Apply to each の並列度は 20 前後を上限とする。

リクエスト予算が緩んだぶん、律速はライセンスではなくサービス保護制限側に移った。

5容量がテナント共有プールになった

2 GB/環境 のハード上限は消えたが、代わりに自分で制御できない変数が増えた。 他部署が Dataverse を使い始めると容量を食い合う。 着手前に Power Platform 管理センター → リソース → 容量 で実際の空きを確認し、 定期的に監視すること。

6区分マスタを7列で共有することの副作用 確認済み・要注意

区分表1本(5行)で7列すべてを賄えることは確認済み。ただしマスタを共有する以上、 列ごとに値域を絞ることができない。

例えば 出荷マーク に 単位区分 用のコードを入れても、Dataverse はルックアップとして 正当なので受け付ける。「その列に入ってよい値か」の検証はどこにも存在しない。

対処:

  • Excel 側の入力規則(データの入力規則 → リスト)で列ごとに候補を絞る
  • 週次の整合性検証フロー(5-4)で、列ごとの値の分布を集計して異常値を検出する

列ごとに厳密な値域が必要になった時点で、区分マスタに区分種別を追加して 複合代替キー(区分種別 + 区分コード)へ移行する。移行は列の再作成を伴うため、 必要になる可能性が少しでもあるなら最初から複合キーにしておくほうが安い。

7初期ロードと定常同期でハッシュ計算が食い違う罠

Power Query で計算したハッシュと Office Script で計算したハッシュは、 日付フォーマット・数値の丸め・空白の扱いのわずかな差で必ず食い違う。 一致させようとせず、6-1 Step 2 の「archiveはハッシュ空、currentは初回同期で埋める」方式にする。

8タイムゾーン設定は後から変えられない

受注日 納期 を「日付と時刻」型で作ってしまうと、後から「日付のみ」に変更できない。 テーブルを作り直すことになる。列を作る瞬間に決める。

9ポーリングトリガー自体がリクエストを消費する

Premium では最小間隔が1分になるが、1分間隔にすると1フローあたり1,440件/日を消費する。 40,000 に対しては軽いが、無意味な消費であることに変わりはない。 「即時性」の要件を確認し、15分で足りるなら15分にする。

10Excel Online コネクタのファイルサイズ上限

500行×59列そのものは軽いが、条件付き書式・入力規則・過去の書式残骸が積もると数MBになる。 上限(約25MB)に近づくと予告なくエラーになる。 定期的に「未使用範囲のクリア」(Ctrl+End が最終行を大きく超えていないか)を確認する。

11200ファイル構造そのものが根本的な負債

最新月しか更新しないなら、過去200ファイルをDataverseに入れる目的は「過去参照」だけ。 参照だけなら Dataverse化は過剰かもしれない(→ 代替案B)。 Premium のライセンス費用を払う理由を説明できるかどうかが、この問いの答えになる。

10代替案

Power Automate Premium の決裁が取れない場合、代替案A が第一候補になる。 Dataverse for Teams が廃止される以上、「Business Standard の範囲で関係データを持つ」手段は SharePoint リストしか残らない。

代替案A — SharePoint リストを本体にする Premium 不可の場合の第一候補

  • 同じ標準コネクタ、フロー構造(技法1〜4)はそのまま流用できる
  • 上限 3,000万アイテム。容量は SharePoint 側(Business Standard で 1TB + 10GB×ユーザー数)
  • 一意制約・ルックアップ・インデックス列は持てる
  • 弱点: 5,000アイテムのリスト表示しきい値(インデックス設計で回避可能)、型が弱い、 代替キーによるUpsertが無い(GUID辞書技法は同じく使えるので実害は小さい)
  • 標準コネクタのみで動くため、Business Standard with Copilot の範囲に収まる(追加費用ゼロ)
  • Excel 側の改修と Office Script はそのまま流用できる。切り替えが必要なのは フロー後半の Dataverse アクション(作成/更新/削除)を SharePoint アクションに差し替える部分だけ
  • 弱点の補足: 列レベルセキュリティが無いため 原価 粗利益 を隠せない。 バックアップはごみ箱(既定93日)に依存し、Dataverse のような時点復元はできない

  • Excel の Power Query「SharePointフォルダーから」で200ファイルを結合し、ピボットで分析
  • 同期障害ゼロ、追加コストゼロ、今日から実行可能
  • 弱点: 書き込み不可、モバイル/アプリ化不可、10万行の結合更新に数分かかる
  • 目的が集計・分析だけなら、これが最善。 Premium のライセンス費用を払う前に必ず検討すべき

代替案C — ローカル Access に統合DBを作る

  • Microsoft 365 Business Standard には Access(Windows PC向け)が含まれる
  • 200ファイルをリンクテーブル/インポートで統合、SQLで自由に集計。10万行は瞬時
  • 弱点: 共有・同時実行に弱い、クラウドではない、モバイル不可
  • 単独PCでの分析用途なら、圧倒的に速く・安く・壊れにくい

代替案D — Excel側を集約する(代替案というより、やるべき前処理)

  • 200ファイル → 年次12ファイル、または「最新月 + アーカイブ1ファイル」に集約
  • スキャン対象・保守対象・初期ロードの手間がすべて激減する
  • 200個のファイルを維持する業務上の理由が「毎月作るから」だけなら、集約を検討する価値が高い
