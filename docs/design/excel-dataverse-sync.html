Design specification

毎月DB → Dataverse 引合検索システム

ローカルPC(Windows 11)上の Excel「毎月DB」を Dataverse に取り込み、新規引合が来たときに過去の類似実績を検索する。Dataverse for Teams の廃止と用途の確定を受けた第2版 — 取り込みは Power Automate ではなく Dataflow で行う。

用途
新規引合時の過去実績検索（約10万行）
利用者
1〜3人（最初は1人）
必要ライセンス
Power Apps のみ
取り込み
Dataflow / 日次 02:00

0前提条件

0-1目的と利用者 確定

項目内容
目的新規引合が来たとき、過去の類似実績を検索して見積の根拠にする
利用者1〜3人。最初は1人で試験運用
操作読み取り専用の検索のみ。データの書き換えは行わない
検索の例「SUS304 20A のボールバルブを ABC商事 に、過去いくらで売ったか」

この目的から導かれる設計方針が3つある。以降の設計はすべてこれに従う。

方針理由
即時同期は不要。日次バッチでよい引合の見積に、昨日時点のデータで支障はない
過去データ(200ファイル)こそが本体検索対象は過去実績。最新月は相対的に重要度が低い
全行を対象とした部分一致検索が必須「SUS304 を含む」で10万行すべてを検索できること。これが要件の核心

0-2業務前提 ヒアリング確定済み・再質問不要

項目確定内容
行の一意キー受注No + 手配票No + sub_no
同期キーの形式3要素を区切り無しで連結。13524 + R08-0234 + 01 → 13524R08-023401
明細行番業務システムから出力不可。取り込み時に出現順で自動採番する
sub_no の採番単位受注No + 手配票No ごと
更新されるファイル最新月の1ファイルのみ。過去200ファイルは確定・不変
削除の扱い物理削除
ファイルの行順変わらない(並べ替えは発生しない)
受注No の月跨ぎ発生しない
1グループの明細数99以下(sub_no は2桁で足りる)
区分表5行のマスタ1本で7つの区分列すべてを賄える
手配票No の空欄存在しない
列名の変更Excel列「摘要」→「手配票No」、論理名 crfff_RNo

0-3ライセンス要件 第2版で変更

必要なのは Power Apps のライセンスであり、Power Automate Premium は不要。

対象必要なライセンス
Microsoft 365Business Standard(現行のまま。Copilot は不要)
Dataflow を所有するアカウントPower Apps(Premium または per app)
検索アプリの利用者 1〜3人Power Apps(Premium または per app)
~~Power Automate Premium~~不要

根拠は Microsoft の公式ドキュメント。

Power Platform 環境でデータフローを作成するには、 Power Apps Premium、Power Apps Per User (P1)、または Power Apps Per App (P2) が必要。

Dataflow は Power Automate のフローではなく Power Platform のデータ統合機能であるため、 Power Automate のライセンス体系（「アプリのコンテキスト内」制約を含む）が適用されない。

着手前の必須確認: per app プランは 2026年1月頃に新規販売を終了したとの情報と、 現在も $5 で提供されているとの情報が食い違っている。 年額で $540 の差になるため、リセラーまたは Microsoft に1件問い合わせること。

モデル駆動アプリは常にプレミアム扱い

モデル駆動アプリは Dataverse 上で動くため、Microsoft 365 付帯ライセンスでは作ることも使うこともできない。 ここに選択の余地はない。per app か Premium のいずれかが、作る人と使う人の全員に必要。

2Excel側に必要な改修

第2版では要件が大幅に減った。 Power Query はワークシートを直接読めるため、 初版で必須としていたテーブル(ListObject)化は不要になった。

2-1コード系列の書式を「文字列」にする 必須

受注No / 手配票No / 商品コード / 得意先コード / 担当者コード
部門コード / 直送先コード / 見積No / 番船 / ﾌﾟﾛｼﾞｪｸﾄ名コード

数値書式のままだと 0001 → 1 になりキーが壊れる。 受注No と 手配票No は同期キーの構成要素なので、ここが崩れると取り込み全体が破綻する。

2-2ファイル配置とファイル名規約

SharePoint: /毎月DB/
    current/  毎月DB_2026-11.xlsx     ← 最新月
    archive/  毎月DB_2026-10.xlsx     ← 確定済み
              ... (200ファイル)
    master/   区分表.xlsx
  • 月次締めで current/ のファイルを archive/ へ移動し、新しい月のファイルを current/ に置く
  • OneDrive の一時ファイル ~$*.xlsx と競合コピー *-<PC名>.xlsx は Power Query 側で除外する

2-3アーカイブの集約 強く推奨

200ファイルを毎回読むと、Dataflow の更新に数十分かかる。 年次12ファイル(または1ファイル)に集約すると、更新が大幅に短縮される。

集約は一度きりの作業で、Power Query で結合して出力するだけ。構築の最初にやる価値がある。

2-4不要になったもの

初版の要件第2版
全ファイルのテーブル化(T_DB)不要。Power Query はシートを直接読む
ensureTable() による自動テーブル化不要
Office Script(334行)不要。Power Query が同等の処理を行う

3-1テーブル一覧

3-4区分列はルックアップではなくテキストにする 第2版で変更

初版では区分列7本を区分マスタへのルックアップにしていた。第2版ではテキスト列に変更する。

ルックアップ(初版)テキスト(第2版)
Dataflow でのマッピング代替キーによる解決が必要。設定が煩雑単純な値のコピー
コードがマスタに無い場合行の作成が失敗する取り込まれる
検索間接参照になり扱いにくいそのまま検索対象になる
参照整合性効く効かない

用途が検索である以上、参照整合性より取り込みの確実性と検索のしやすさを優先する。 区分名を表示したい場合は、区分マスタを別テーブルとして残し、モデル駆動アプリ側で参照する。

初版で懸念した「区分コードが空だと404で行の作成が失敗する」問題も、テキスト化により消滅する。

将来、区分による絞り込みドロップダウンや参照整合性が必要になった時点でルックアップ化できる。 列の型変更は再作成を伴うが、検索用途で先にルックアップを作る理由は無い。

項目正解間違えるとどうなるか

4Dataflow 設計

4-1全体方針

項目設定
種類標準データフロー(Dataverse にデータを格納)
ソースSharePoint フォルダー(/毎月DB/)
対象テーブルcrfff_jisseki(既存テーブルに読み込む)

4-2Power Query の処理手順

1. SharePoint フォルダーに接続（サイトURL を指定）
2. 一時ファイル・競合コピーを除外
3. Excel ブックを展開し、ワークシートを取得
4. ヘッダーを昇格し、不要な行を除去
5. 列名を論理名に変更（59列）
6. 型を変換（日付・10進数・テキスト）
7. 受注No + 手配票No ごとに出現順で sub_no を採番
8. sync_key を生成
9. Dataverse にマッピングして読み込む

4-3主要な M コード

ファイルの絞り込み

// OneDrive の一時ファイルと競合コピーを除外する
FilteredFiles = Table.SelectRows(Source, each
    not Text.StartsWith([Name], "~$")
    and Text.EndsWith([Name], ".xlsx")
    and not Text.Contains([Name], "-DESKTOP-")
)

ワークシートの展開

// テーブル(ListObject)ではなくワークシートを直接読む
Workbooks   = Table.AddColumn(FilteredFiles, "Data", each Excel.Workbook([Content])),
Expanded    = Table.ExpandTableColumn(Workbooks, "Data", {"Name","Kind","Data"},
                                      {"SheetName","Kind","SheetData"}),
SheetsOnly  = Table.SelectRows(Expanded, each [Kind] = "Sheet"),

Kind = "Sheet" が重要。 初版の Kind = "Table" だと、 テーブル化していないファイルが読み飛ばされる。

sub_no の採番（受注No + 手配票No 単位の出現順）

// Table.Group はグループ内の元の行順を保持するため、
// インデックスがそのまま「出現順」になる
Grouped = Table.Group(
    Typed,
    {"crfff_order_no", "crfff_RNo"},
    {{"g", each Table.AddIndexColumn(_, "crfff_sub_no", 1, 1, Int64.Type), type table}}
),

ExpandedSubNo = Table.ExpandTableColumn(
    Grouped, "g",
    List.RemoveItems(Table.ColumnNames(Typed), {"crfff_order_no", "crfff_RNo"})
        & {"crfff_sub_no"}
),

sync_key の生成

// 3要素を区切り無しで連結する  例: 13524 + R08-0234 + 01 → 13524R08-023401
AddedSyncKey = Table.AddColumn(ExpandedSubNo, "crfff_sync_key",
    each [crfff_order_no]
       & [crfff_RNo]
       & Text.PadStart(Text.From([crfff_sub_no]), 2, "0"),
    type text
),

    if [crfff_order_no] = null or Text.Trim([crfff_order_no]) = "" then

5検索アプリ設計

5-1キャンバスアプリを使わない 最重要

Power Apps のキャンバスアプリでは、10万行の部分一致検索ができない。

キャンバスアプリには委任(delegation) の仕組みがあり、サーバー側で処理できないクエリは 先頭500件(設定で最大2,000件)しか取得しない。

関数Dataverse に対して委任されるか
StartsWith / EndsWithされる
Contains(部分一致)されない
Search()されない

上限を 2,000 に引き上げても、非委任のクエリがテーブル全体を検索するようにはならない。 ローカルで処理できる件数が増えるだけ。

引合検索では 規格・型番 が「ボールバルブ SUS304 20A」のような形になるため、 前方一致では実用にならず、部分一致が必須。したがってキャンバスアプリは要件を満たさない。

5-2モデル駆動アプリ + Dataverse 検索

モデル駆動アプリのビューは FetchXML で動くため、委任制限が無く全行が対象になる。

構築手順

1. Power Platform 管理センターで Dataverse 検索を有効化
     環境 → 設定 → 製品 → 機能 → Dataverse search → オン

2. 検索対象列を「クイック検索ビュー」に登録
     商品コード / 規格・型番 / 商品名 / 得意先名１ / 得意先コード

3. 既定のビューを作成
     列: 受注日 / 得意先名１ / 商品コード / 商品名 / 規格・型番 / ｻｲｽﾞ /
         受注数 / 単価 / 売単価 / 原価 / 粗利益 / 納期 / 受注No / 手配票No
     並べ替え: 受注日 降順

4. モデル駆動アプリを新規作成し、毎月DB実績テーブルを追加

コードは1行も書かない。半日程度の設定作業で完成する。

7見落としやすい弱点

重要度順。

1ライセンスとDataverse容量を確認せずに着手すること

per app が購入できるかで年 $540、テナント既定容量が使えるかで設計の可否が変わる(0-5)。 テーブルを作る前に両方を確認すること。

2キャンバスアプリで作ってしまうこと

最も踏みやすい地雷。Power Apps の既定の作り方がキャンバスアプリであるため、 何も考えずに作ると先頭2,000行しか検索しないアプリができあがる。 しかも動いているように見えるため、気づくのが遅れる。必ずモデル駆動アプリで作ること(5-1)。

3Dataflow の所有者を個人アカウントにすること

所有者の異動・退職・パスワード変更で更新が無言で止まる。 専用アカウントを用意し、そこに Power Apps ライセンスを割り当てること。

4タイムゾーン設定は後から変えられない

受注日 納期 を「日付と時刻」型で作ると、後から「日付のみ」に変更できない。 テーブルを作り直すことになる。列を作る瞬間に決める。

5自動型検出による取り込みの揺れ

Power Query の自動型検出を有効のままにすると、ファイルによって列の型が変わり、 ある月だけ取り込みが失敗する。必ず無効化し、型を明示すること(4-4)。

6アーカイブ200ファイルによる更新時間

削除検出と200ファイルの結合が重なると、更新が数十分になる。 年次12ファイルへの集約(2-3)を構築時にやっておくこと。

7200ファイル構造そのもの

最新月しか更新しないのに、ファイルが200個ある状態は保守負債。 集約は検索システムのためだけでなく、業務運用としても整理の価値がある。

8代替案

代替案A — Excel + Power Query(追加費用ゼロ)

Dataverse を使わず、Excel のブックで完結させる。

Excel ブック
 └ Power Query で archive の200ファイルを結合
    └ データモデルに読み込む
       └ テキストフィルター(指定の値を含む)で検索
本設計(Dataverse)代替案A(Excel)
月額$15〜$60$0
全行の部分一致検索できるできる(テキストフィルター)
複数列の横断検索できるできない(列ごとに指定)
表記ゆれ強い弱い
モバイル可不可
更新自動(日次)デスクトップ版 Excel で手動(月1回)
構築時間1〜2日半日

「列を指定した部分一致で足りる」なら、代替案Aで要件を満たす。 本設計を選ぶ判断材料は、横断的な全文検索・表記ゆれ耐性・モバイルの3点に絞られる。 費用ゼロ・半日で試せるため、本設計に着手する前に代替案Aを作って検証することを推奨する。 作った Power Query は本設計の Dataflow にそのまま流用できるため、無駄にならない。

代替案B — SharePoint リスト

Dataverse ではなく SharePoint リストに取り込む。標準コネクタのみで動くため追加費用ゼロ。 ただし Dataflow は使えず Power Automate が必要になり、全文検索も Dataverse 検索ほど強くない。 本用途では代替案A のほうが素直。

代替案C — ローカル Access

Business Standard に Access が含まれる。10万行は瞬時。単独PCでの利用なら最速・最安。 共有・モバイルは不可。
